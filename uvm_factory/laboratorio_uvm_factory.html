Laboratorio guiado: la fábrica de UVM

1 de octubre de 2026

1. Introducción y objetivos

Al terminar este laboratorio sabrás registrar clases en la fábrica de UVM, crearlas de forma que puedan sustituirse sin tocar el código del entorno, y aplicar overrides de tipo y de instancia prediciendo exactamente qué clase se construye. El laboratorio dura unas 4 horas: 1 hora de teoría y 5 prácticas sobre un mismo testbench con dos agentes.

Objetivos de aprendizaje

  1. Explicar qué problema resuelve la fábrica y por qué new() no basta.
  2. Registrar componentes y objetos con las macros adecuadas y entender qué generan.
  3. Crear objetos con type_id::create(), incluyendo el argumento de contexto para objetos.
  4. Aplicar overrides de tipo y de instancia, por tipo y por nombre, desde código y desde la línea de comandos.
  5. Predecir el resultado cuando se combinan varios overrides: precedencia, orden, reemplazo y encadenamiento.
  6. Registrar y sustituir clases parametrizadas.
  7. Depurar con factory.print() y debug_create_by_type().

Requisitos previos

  • SystemVerilog orientado a objetos: herencia, métodos virtuales, $cast, clases parametrizadas.
  • UVM básico: componentes, fases, agente con driver, monitor y secuenciador, y uvm_config_db para la interfaz virtual.
  • Un simulador con UVM 1.2 o IEEE 1800.2: Questa, VCS, Xcelium, Riviera-PRO o EDA Playground.

Convenciones

  • Cada práctica tiene: objetivo, código, tareas con // TODO, qué observar y solución plegada.
  • Todas las prácticas parten del testbench de la Sección 4 y añaden clases derivadas.
  • Cada clase imprime su propio nombre de tipo, de modo que el log dice qué construyó la fábrica.

2. Teoría I: registro y creación

La fábrica es un registro global de tipos que construye objetos por encargo: el código pide "un simple_driver" y la fábrica decide si entrega ese tipo o una clase derivada configurada por el test. Así un test cambia el comportamiento del entorno sin editarlo, que es la base de la reutilización en UVM.

2.1 El problema que resuelve

Con drv = new("drv", this); el tipo queda fijado en el código del agente. Si un test necesita un driver que inyecte errores, habría que editar el agente o duplicarlo. Con drv = simple_driver::type_id::create("drv", this); el agente sigue pidiendo un simple_driver, pero el test puede indicar a la fábrica que entregue un err_driver en su lugar. Gracias al polimorfismo, el agente lo maneja con el mismo handle.

agente: simple_driver::type_id::create("drv", this) │ ▼ fábrica: ¿override de instancia para "uvm_test_top.env.agt0.drv"? ── sí ──▶ ese tipo │ no ▼ ¿override de tipo para simple_driver? ── sí ──▶ ese tipo │ no (y se repite la búsqueda ▼ para el tipo resultante) construye simple_driver

2.2 Registro con macros

MacroParaRegistra el nombre
`uvm_component_utils(T)Clases derivadas de uvm_component (constructor new(string name, uvm_component parent))Sí
`uvm_object_utils(T)Clases derivadas de uvm_object: items, secuencias, configuraciones (constructor new(string name = "..."))Sí
`uvm_component_param_utils(T#(P))Componentes parametrizadosNo: solo por tipo
`uvm_object_param_utils(T#(P))Objetos parametrizadosNo: solo por tipo
`uvm_*_utils_begin / _endIgual que las anteriores, añadiendo macros de campo `uvm_field_*Sí

Simplificando, `uvm_component_utils(simple_driver) genera:

typedef uvm_component_registry #(simple_driver, "simple_driver") type_id;
static function type_id get_type();      return type_id::get(); endfunction
virtual function uvm_object_wrapper get_object_type(); return type_id::get(); endfunction
const static string type_name = "simple_driver";
virtual function string get_type_name(); return type_name; endfunction

type_id es una clase proxy (un singleton) que representa el tipo ante la fábrica. Al cargarse el paquete, cada proxy se registra automáticamente. get_type() devuelve ese proxy y es lo que se pasa a los métodos de override. Para objetos, la macro además genera create().

2.3 Creación con type_id::create

// Componentes: nombre y padre (el padre define la ruta jerárquica)
drv = simple_driver::type_id::create("drv", this);

// Objetos: nombre, padre opcional y contexto (ruta usada para overrides de instancia)
req = simple_item::type_id::create("req", null, get_full_name());
  • Para componentes, la ruta de instancia es {parent.get_full_name(), ".", name}.
  • Para objetos, la ruta es {contxt, ".", name}; si no das contexto, es solo name. Sin contexto, un override de instancia para un objeto casi nunca coincide.
  • create hace internamente un $cast al tipo pedido; si el override entrega una clase incompatible, falla con uvm_fatal.

2.4 Acceso a la fábrica

uvm_factory factory = uvm_factory::get();  // UVM 1.2 y 1800.2
factory.print();                           // overrides registrados (y tipos, con print(1))

En UVM 1.1 existía una variable global factory; en UVM 1.2 está obsoleta y en 1800.2 se usa siempre uvm_factory::get().

3. Teoría II: overrides y sus reglas

Un override indica a la fábrica "cuando pidan el tipo A, entrega el tipo B". Puede aplicarse a todas las creaciones de A (override de tipo) o solo a las que ocurren en rutas concretas (override de instancia). B debe derivar de A para que el $cast interno funcione.

3.1 Las formas de declarar un override

AlcanceDesde un componente (rutas relativas a él)Mediante el proxyLínea de comandos
Tipo, por tiposet_type_override_by_type(A::get_type(), B::get_type(), replace = 1)A::type_id::set_type_override(B::get_type())—
Instancia, por tiposet_inst_override_by_type("env.agt0.drv", A::get_type(), B::get_type())A::type_id::set_inst_override(B::get_type(), "env.agt0.drv", this)—
Tipo, por nombreset_type_override("A", "B", replace = 1)—+uvm_set_type_override=A,B
Instancia, por nombreset_inst_override("env.agt0.drv", "A", "B")—+uvm_set_inst_override=A,B,uvm_test_top.env.agt0.drv

Los métodos de componente convierten la ruta relativa en absoluta anteponiendo get_full_name(). Las rutas de instancia admiten comodines (*, ?). Los métodos de uvm_factory (factory.set_inst_override_by_type(A::get_type(), B::get_type(), "uvm_test_top.env.agt0.drv")) usan siempre rutas absolutas.

Prefiere las variantes por tipo: el compilador comprueba que las clases existen. Las variantes por nombre fallan en simulación si hay una errata, pero son las únicas disponibles desde la línea de comandos.

3.2 Reglas de resolución

  1. Instancia antes que tipo: si un override de instancia coincide con la ruta, se usa, aunque exista un override de tipo registrado después.
  2. Entre overrides de instancia, gana el primero registrado que coincida. Registra primero los más específicos y después los más generales.
  3. Entre overrides de tipo para el mismo tipo original, con replace = 1 (por defecto) el nuevo sustituye al anterior; con replace = 0 se conserva el existente.
  4. Encadenamiento: si A → B y B → C, pedir A produce C. La fábrica repite la búsqueda con el tipo resultante y detecta ciclos.
  5. Momento: un override solo afecta a las llamadas a create que ocurren después de registrarlo. Lo habitual es declararlo en build_phase del test, antes de crear el env.
  6. Solo create: un objeto construido con new() nunca se sustituye.

3.3 Qué sustituir y qué no

  • Buenos candidatos: drivers con inyección de errores o temporización distinta, items con restricciones adicionales, secuencias, scoreboards o modelos de referencia alternativos, objetos de configuración con valores por defecto distintos.
  • El override solo puede añadir o cambiar comportamiento a través de métodos virtuales y restricciones. Si el agente llama a un método no virtual, la clase derivada no puede cambiarlo: diseña puntos de extensión (virtual task drive_item(...)).
  • La fábrica no cambia interfaces ni conexiones TLM: la clase derivada debe ser compatible con el uso que hace el padre.

3.4 Errores comunes

SíntomaCausa probable
El override no tiene efectoEl objeto se crea con new(); o el override se registra después del create; o la ruta de instancia no coincide
El override no tiene efecto y la clase derivada imprime el nombre de la baseFalta la macro `uvm_*_utils en la clase derivada: hereda el type_id de la base y get_type() devuelve el proxy equivocado
Error de compilación en type_idClase sin macro de registro, o `uvm_object_utils usada en un componente (o al revés)
uvm_fatal al crearEl tipo de override no deriva del tipo pedido
Override de instancia sobre items sin efectoEl item se crea sin contexto: create("req") en lugar de create("req", null, get_full_name())
Override por nombre ignorado con avisoErrata en el nombre, o clase parametrizada (no registrada por nombre)

4. Testbench base

El testbench tiene dos agentes idénticos (agt0, agt1) sobre dos interfaces. Cada driver y cada secuencia imprimen su tipo real, así que el log muestra el efecto de cada override. Compílalo y verifica que funciona antes de empezar.

simple_if.sv

interface simple_if (input logic clk);
  logic       valid;
  logic [7:0] data;
endinterface

factory_lab_pkg.sv

package factory_lab_pkg;
  import uvm_pkg::*;
  `include "uvm_macros.svh"

  // ---------------- Item ----------------
  class simple_item extends uvm_sequence_item;
    rand bit [7:0] data;
    `uvm_object_utils_begin(simple_item)
      `uvm_field_int(data, UVM_DEFAULT)
    `uvm_object_utils_end
    function new(string name = "simple_item"); super.new(name); endfunction
  endclass

  // ---------------- Driver ----------------
  class simple_driver extends uvm_driver #(simple_item);
    `uvm_component_utils(simple_driver)
    virtual simple_if vif;
    function new(string name, uvm_component parent); super.new(name, parent); endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      if (!uvm_config_db #(virtual simple_if)::get(this, "", "vif", vif))
        `uvm_fatal("NOVIF", {"Falta 'vif' para ", get_full_name()})
    endfunction

    // Punto de extensión: las clases derivadas lo sobrescriben
    virtual task drive_item(simple_item it);
      @(posedge vif.clk);
      vif.valid <= 1; vif.data <= it.data;
      @(posedge vif.clk);
      vif.valid <= 0;
    endtask

    task run_phase(uvm_phase phase);
      `uvm_info("DRV", {"Construido como ", get_type_name()}, UVM_LOW)
      vif.valid <= 0;
      forever begin
        seq_item_port.get_next_item(req);
        `uvm_info("DRV", $sformatf("item %s data=0x%02h", req.get_type_name(), req.data), UVM_MEDIUM)
        drive_item(req);
        seq_item_port.item_done();
      end
    endtask
  endclass

  // ---------------- Monitor ----------------
  class simple_monitor extends uvm_monitor;
    `uvm_component_utils(simple_monitor)
    virtual simple_if vif;
    function new(string name, uvm_component parent); super.new(name, parent); endfunction
    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      if (!uvm_config_db #(virtual simple_if)::get(this, "", "vif", vif))
        `uvm_fatal("NOVIF", {"Falta 'vif' para ", get_full_name()})
    endfunction
    task run_phase(uvm_phase phase);
      forever begin
        @(posedge vif.clk);
        if (vif.valid) `uvm_info("MON", $sformatf("t=%0t data=0x%02h", $time, vif.data), UVM_MEDIUM)
      end
    endtask
  endclass

  typedef uvm_sequencer #(simple_item) simple_sequencer;

  // ---------------- Agente ----------------
  class simple_agent extends uvm_agent;
    `uvm_component_utils(simple_agent)
    simple_driver    drv;
    simple_monitor   mon;
    simple_sequencer sqr;
    function new(string name, uvm_component parent); super.new(name, parent); endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      // TODO 1: crea mon, drv y sqr con la fábrica (nombres "mon", "drv", "sqr")
    endfunction

    function void connect_phase(uvm_phase phase);
      drv.seq_item_port.connect(sqr.seq_item_export);
    endfunction
  endclass

  // ---------------- Env ----------------
  class simple_env extends uvm_env;
    `uvm_component_utils(simple_env)
    simple_agent agt[2];
    function new(string name, uvm_component parent); super.new(name, parent); endfunction
    function void build_phase(uvm_phase phase);
      foreach (agt[i])
        agt[i] = simple_agent::type_id::create($sformatf("agt%0d", i), this);
    endfunction
  endclass

  // ---------------- Secuencia ----------------
  class simple_seq extends uvm_sequence #(simple_item);
    `uvm_object_utils(simple_seq)
    int unsigned n_items = 4;
    function new(string name = "simple_seq"); super.new(name); endfunction
    task body();
      `uvm_info("SEQ", {"Construida como ", get_type_name()}, UVM_LOW)
      repeat (n_items) begin
        // TODO 2: crea req con la fábrica, pasando get_full_name() como contexto
        start_item(req);
        if (!req.randomize()) `uvm_error("RAND", "randomize falló")
        finish_item(req);
      end
    endtask
  endclass

  // ---------------- Test base ----------------
  class base_test extends uvm_test;
    `uvm_component_utils(base_test)
    simple_env env;
    function new(string name, uvm_component parent); super.new(name, parent); endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      env = simple_env::type_id::create("env", this);
    endfunction

    function void end_of_elaboration_phase(uvm_phase phase);
      uvm_top.print_topology();
      uvm_factory::get().print();
    endfunction

    task run_phase(uvm_phase phase);
      phase.raise_objection(this);
      foreach (env.agt[i]) begin
        automatic int k = i;
        fork begin
          simple_seq seq = simple_seq::type_id::create("seq", null, env.agt[k].sqr.get_full_name());
          seq.start(env.agt[k].sqr);
        end join_none
      end
      wait fork;
      phase.drop_objection(this);
    endtask
  endclass
endpackage

7. Práctica 3: overrides de instancia y precedencia

8. Práctica 4: por nombre, línea de comandos y clases parametrizadas

Objetivo: aplicar overrides sin recompilar, crear objetos a partir de un string y entender por qué las clases parametrizadas solo admiten overrides por tipo.

8.1 Overrides desde la línea de comandos

Sin modificar código, ejecuta base_test con cada una de estas opciones y anota el resultado:

  1. +uvm_set_type_override=simple_driver,slow_driver
  2. +uvm_set_inst_override=simple_driver,err_driver,uvm_test_top.env.agt0.drv
  3. Las dos anteriores a la vez.
  4. +uvm_set_type_override=simple_driver,slowdriver (con errata).

Clases parametrizadas:

  • Las macros _param_utils no registran un nombre, porque cada especialización es un tipo distinto. El override por nombre provoca un aviso de tipo no registrado y no tiene efecto. Por eso +uvm_set_type_override tampoco funciona con ellas.
  • param_scoreboard #(8) y strict_scoreboard #(16) no están relacionados por herencia (strict_scoreboard #(16) deriva de param_scoreboard #(16)). La llamada compila, porque los argumentos son proxies genéricos, pero el create fallará con un uvm_fatal de cast.

10. Evaluación y buenas prácticas

Responde las diez preguntas sin consultar el laboratorio; si fallas más de dos, repasa la Sección 3 y repite la Práctica 3.

10.1 Preguntas

  1. ¿Qué tres cosas genera `uvm_component_utils(T) que la fábrica necesita?
  2. ¿Por qué un objeto construido con new() no puede sustituirse?
  3. ¿Cuál es la ruta de instancia de my_cfg::type_id::create("cfg", null, "uvm_test_top.env")? ¿Y de my_cfg::type_id::create("cfg")?
  4. Hay un override de tipo A → B y otro de instancia A → C para env.agt0.x, registrado antes. ¿Qué se construye en env.agt0.x y en env.agt1.x?
  5. Se registran, en este orden, los overrides de instancia "env.*" → B y "env.agt0.x" → C. ¿Qué obtiene env.agt0.x?
  6. ¿Qué ocurre con A → B seguido de A → C con replace = 0?
  7. ¿Qué produce pedir A si existen A → B y B → C?
  8. ¿Por qué no se puede usar +uvm_set_type_override con una clase registrada con `uvm_component_param_utils?
  9. Una clase derivada no tiene macro de registro. ¿Qué efecto tiene sobre un override hacia ella?
  10. ¿En qué punto del test debe registrarse un override del env, y por qué uno del driver puede registrarse algo más tarde?
10.2 Respuestas
  1. El proxy type_id (un uvm_component_registry que se registra en la fábrica), get_type() y get_type_name()/get_object_type().
  2. Porque new() es una construcción directa de SystemVerilog con tipo fijo: la fábrica nunca participa.
  3. uvm_test_top.env.cfg. Sin contexto, solo cfg.
  4. C en env.agt0.x (instancia gana) y B en env.agt1.x. El orden de registro no cambia esto.
  5. B: entre overrides de instancia gana el primero registrado que coincide, y "env.*" coincide.
  6. Se conserva A → B.
  7. C, por encadenamiento.
  8. Porque las macros parametrizadas no registran un nombre de tipo, y la línea de comandos solo trabaja por nombre.
  9. Hereda el type_id de la base: Derivada::get_type() devuelve el proxy de la base, el override queda como A → A y no tiene efecto.
  10. El del env, antes de crearlo (antes de super.build_phase si la base lo crea ahí). El del driver puede ir más tarde dentro del build_phase del test, porque el driver se crea en build_phase del agente, que ocurre después; aun así, la costumbre segura es registrarlos todos al principio.

10.3 Buenas prácticas

  • Registra todas las clases (componentes, objetos, items, secuencias, configuraciones y tests) con su macro.
  • Crea siempre con type_id::create; nunca uses new() para nada que un test pueda querer sustituir.
  • Pasa contexto (get_full_name()) al crear objetos si quieres permitir overrides de instancia sobre ellos.
  • Registra los overrides al principio de build_phase del test, antes de crear el env.
  • Prefiere overrides por tipo en el código; reserva los de nombre para la línea de comandos.
  • Ordena los overrides de instancia del más específico al más general.
  • Diseña puntos de extensión virtuales (drive_item, calc_expected) para que las clases derivadas tengan qué sustituir.
  • Usa typedef para especializaciones de clases parametrizadas.
  • Imprime factory.print() y la topología en end_of_elaboration_phase del test base: cuestan poco y ahorran horas.
