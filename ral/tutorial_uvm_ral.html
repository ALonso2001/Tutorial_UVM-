Tutorial: el RAL de UVM desde cero

13 de octubre de 2026

1. Introducción y ruta

En este tutorial construirás, paso a paso, un entorno UVM completo con modelo de registros (RAL, Register Abstraction Layer) para un periférico sencillo con seis registros y una memoria de 32 palabras. Al final sabrás describir registros y memorias, conectar el modelo al bus con un adaptador y un predictor, configurar el acceso por backdoor y usar todas las operaciones de acceso, por el bus y por backdoor.

Objetivos de aprendizaje

  1. Explicar qué resuelve el RAL y qué son los valores deseado, espejo (mirror) y real.
  2. Describir campos, registros, memorias, bloques y mapas, y conocer el proceso exacto de instanciación.
  3. Elegir la política de acceso de cada campo entre todas las que define UVM, y conocer los tipos especiales de registros.
  4. Implementar un adaptador y conectar un predictor explícito, entendiendo por qué son necesarios.
  5. Configurar el backdoor por rutas HDL e implementar un backdoor de usuario.
  6. Usar write, read, set, update, mirror, predict, peek, poke y los accesos a memoria por frontdoor y backdoor.
  7. Aplicar las secuencias de verificación de registros que trae UVM.

Requisitos previos

  • SystemVerilog y UVM básico: agentes, secuencias y driver, fases, fábrica, uvm_config_db, puertos de análisis.
  • Un simulador con UVM 1.2 o IEEE 1800.2 y acceso DPI a la jerarquía (Questa, VCS, Xcelium o Riviera-PRO). En EDA Playground funciona con Riviera-PRO.

2. Qué es el RAL

El RAL es un modelo en SystemVerilog de los registros y memorias del DUT: cada registro es un objeto con sus campos, su dirección, su valor de reset y su política de acceso. Las secuencias acceden a los registros por nombre (rm.CTRL.write(...)) en lugar de por dirección y valor crudo, y el modelo se encarga de traducir cada acceso a transacciones del bus y de llevar la cuenta del valor que debería tener cada registro.

2.1 Qué problemas resuelve

  • Independencia del bus: la misma secuencia de registros funciona si el periférico se conecta por APB, AHB o AXI; solo cambia el adaptador.
  • Mantenimiento: si una dirección o un campo cambia, se cambia el modelo (a menudo generado automáticamente desde IP-XACT o SystemRDL), no cada secuencia.
  • Comprobación: el modelo predice el valor de cada registro y permite compararlo con el DUT.
  • Acceso rápido: el backdoor lee y escribe el almacenamiento del DUT directamente, en tiempo cero, sin usar el bus.
  • Pruebas automáticas: UVM incluye secuencias que verifican valores de reset, cada bit de cada registro y las memorias sin escribir código específico.

3. El DUT: un periférico con registros y memoria

El DUT, regmem_dut, es un esclavo APB simplificado (sin estados de espera, pready siempre a 1) con seis registros de 32 bits y una memoria de 32 palabras de 32 bits. Cuando se escribe un comando, el periférico simula una operación que tarda unos ciclos y lo indica en sus registros de estado e interrupción.

Con OPCODE = 0xF, ERR_CNT se incrementa e INT_STAT.ERR_IRQ = 1.

3.3 RTL

Observa los nombres de las señales internas (en_q, presc_q, scratch_q, mem…): son las rutas que usará el backdoor. CTRL se guarda en señales separadas por campo a propósito, para practicar rutas HDL por trozos (slices).

regmem_dut.sv

`timescale 1ns/1ps
module regmem_dut (
  input  logic        clk,
  input  logic        rst_n,
  input  logic        psel,
  input  logic        penable,
  input  logic        pwrite,
  input  logic [7:0]  paddr,
  input  logic [31:0] pwdata,
  output logic [31:0] prdata,
  output logic        pready,
  output logic        irq
);
  // ---------------- Almacenamiento ----------------
  // CTRL (un registro por campo)
  logic        en_q;
  logic [1:0]  mode_q;
  logic        irq_en_q;
  logic [7:0]  presc_q;
  // STATUS
  logic        busy_q;
  logic        done_q;
  logic [7:0]  err_cnt_q;
  logic [2:0]  busy_cnt;
  // INT_STAT: bit 0 DONE_IRQ, bit 1 ERR_IRQ
  logic [1:0]  int_stat_q;
  // SCRATCH
  logic [31:0] scratch_q;
  // ID (constante)
  wire  [31:0] id_w = 32'h5A5A_0001;
  // Memoria BUF
  logic [31:0] mem [0:31];

  wire wr_en  = psel && penable && pwrite;
  wire is_mem = paddr[7];

  assign pready = 1'b1;
  assign irq    = irq_en_q && (|int_stat_q);

  // ---------------- Escritura de registros y comportamiento ----------------
  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
      en_q       <= 1'b0;
      mode_q     <= 2'b0;
      irq_en_q   <= 1'b0;
      presc_q    <= 8'h01;
      busy_q     <= 1'b0;
      done_q     <= 1'b0;
      err_cnt_q  <= 8'h0;
      busy_cnt   <= 3'd0;
      int_stat_q <= 2'b0;
      scratch_q  <= 32'h0;
    end
    else begin
      // Operación en curso
      if (busy_q) begin
        if (busy_cnt == 0) begin
          busy_q        <= 1'b0;
          done_q        <= 1'b1;
          int_stat_q[0] <= 1'b1;
        end
        else busy_cnt <= busy_cnt - 1;
      end

      // Accesos de escritura del bus
      if (wr_en && !is_mem) begin
        case (paddr)
          8'h00: begin
            en_q     <= pwdata[0];
            mode_q   <= pwdata[2:1];
            irq_en_q <= pwdata[3];
            presc_q  <= pwdata[15:8];
          end
          8'h08: int_stat_q <= int_stat_q & ~pwdata[1:0];      // W1C
          8'h0C: if (en_q && pwdata[3:0] != 4'h0) begin
                   if (pwdata[3:0] == 4'hF) begin               // comando inválido
                     err_cnt_q     <= err_cnt_q + 1;
                     int_stat_q[1] <= 1'b1;
                   end
                   else begin                                   // operación de 4 ciclos
                     busy_q   <= 1'b1;
                     done_q   <= 1'b0;
                     busy_cnt <= 3'd3;
                   end
                 end
`ifdef BUG_SCRATCH
          8'h10: scratch_q <= {1'b0, pwdata[30:0]};             // error inyectado: pierde el bit 31
`else
          8'h10: scratch_q <= pwdata;
`endif
          default: ;
        endcase
      end
    end
  end

  // ---------------- Escritura de memoria (sin reset) ----------------
  always_ff @(posedge clk)
    if (wr_en && is_mem) mem[paddr[6:2]] <= pwdata;

  // ---------------- Lectura ----------------
  always_comb begin
    prdata = 32'h0;
    if (psel && !pwrite) begin
      if (is_mem) prdata = mem[paddr[6:2]];
      else case (paddr)
        8'h00: prdata = {16'h0, presc_q, 4'h0, irq_en_q, mode_q, en_q};
        8'h04: prdata = {20'h0, err_cnt_q, 2'b00, done_q, busy_q};
        8'h08: prdata = {30'h0, int_stat_q};
        8'h0C: prdata = 32'h0;                                  // CMD es de solo escritura
        8'h10: prdata = scratch_q;
        8'h14: prdata = id_w;
        default: prdata = 32'h0;
      endcase
    end
  end
endmodule

4. El agente APB

El RAL no sustituye al agente del bus: lo usa. Necesitamos un agente APB normal, con un item, un driver que ejecute transferencias y un monitor que publique cada transferencia observada por un puerto de análisis (lo usará el predictor).

4.1 Protocolo usado

Cada transferencia tiene dos ciclos: setup (psel = 1, penable = 0, dirección y datos válidos) y access (penable = 1). Como pready es siempre 1, la transferencia termina en el flanco al final del ciclo de access: ahí el DUT captura la escritura y el driver captura prdata en una lectura.

apb_if.sv

`timescale 1ns/1ps
interface apb_if (input logic clk, input logic rst_n);
  logic        psel;
  logic        penable;
  logic        pwrite;
  logic [7:0]  paddr;
  logic [31:0] pwdata;
  logic [31:0] prdata;
  logic        pready;
endinterface

apb_pkg.sv

`timescale 1ns/1ps
package apb_pkg;
  import uvm_pkg::*;
  `include "uvm_macros.svh"

  class apb_item extends uvm_sequence_item;
    rand bit        write;
    rand bit [7:0]  addr;
    rand bit [31:0] data;     // dato escrito, o dato leído tras la transferencia
    `uvm_object_utils_begin(apb_item)
      `uvm_field_int(write, UVM_DEFAULT)
      `uvm_field_int(addr,  UVM_DEFAULT)
      `uvm_field_int(data,  UVM_DEFAULT)
    `uvm_object_utils_end
    function new(string name = "apb_item"); super.new(name); endfunction
    function string convert2string();
      return $sformatf("%s addr=0x%02h data=0x%08h", write ? "W" : "R", addr, data);
    endfunction
  endclass

  typedef uvm_sequencer #(apb_item) apb_sequencer;

  class apb_driver extends uvm_driver #(apb_item);
    `uvm_component_utils(apb_driver)
    virtual apb_if vif;
    function new(string name, uvm_component parent); super.new(name, parent); endfunction

    function void build_phase(uvm_phase phase);
      if (!uvm_config_db #(virtual apb_if)::get(this, "", "vif", vif))
        `uvm_fatal("NOVIF", "apb_driver sin interfaz")
    endfunction

    task run_phase(uvm_phase phase);
      vif.psel    <= 1'b0;
      vif.penable <= 1'b0;
      wait (vif.rst_n === 1'b1);
      forever begin
        seq_item_port.get_next_item(req);
        @(posedge vif.clk);                       // ciclo de setup
        vif.psel    <= 1'b1;
        vif.penable <= 1'b0;
        vif.pwrite  <= req.write;
        vif.paddr   <= req.addr;
        vif.pwdata  <= req.write ? req.data : 32'h0;
        @(posedge vif.clk);                       // ciclo de access
        vif.penable <= 1'b1;
        @(posedge vif.clk);                       // fin de la transferencia (pready = 1)
        if (!req.write) req.data = vif.prdata;    // la respuesta vuelve en el propio item
        vif.psel    <= 1'b0;
        vif.penable <= 1'b0;
        seq_item_port.item_done();
      end
    endtask
  endclass

  class apb_monitor extends uvm_monitor;
    `uvm_component_utils(apb_monitor)
    virtual apb_if vif;
    uvm_analysis_port #(apb_item) ap;
    function new(string name, uvm_component parent); super.new(name, parent); endfunction

    function void build_phase(uvm_phase phase);
      ap = new("ap", this);
      if (!uvm_config_db #(virtual apb_if)::get(this, "", "vif", vif))
        `uvm_fatal("NOVIF", "apb_monitor sin interfaz")
    endfunction

    task run_phase(uvm_phase phase);
      forever begin
        @(posedge vif.clk);
        if (vif.psel && vif.penable && vif.pready) begin
          apb_item tr = apb_item::type_id::create("tr");
          tr.write = vif.pwrite;
          tr.addr  = vif.paddr;
          tr.data  = vif.pwrite ? vif.pwdata : vif.prdata;
          `uvm_info("APB", tr.convert2string(), UVM_MEDIUM)
          ap.write(tr);
        end
      end
    endtask
  endclass

  class apb_agent extends uvm_agent;
    `uvm_component_utils(apb_agent)
    apb_sequencer sqr;
    apb_driver    drv;
    apb_monitor   mon;
    function new(string name, uvm_component parent); super.new(name, parent); endfunction
    function void build_phase(uvm_phase phase);
      sqr = apb_sequencer::type_id::create("sqr", this);
      drv = apb_driver::type_id::create("drv", this);
      mon = apb_monitor::type_id::create("mon", this);
    endfunction
    function void connect_phase(uvm_phase phase);
      drv.seq_item_port.connect(sqr.seq_item_export);
    endfunction
  endclass

  // Secuencia cruda (sin RAL); la usaremos para demostrar el predictor
  class apb_raw_write_seq extends uvm_sequence #(apb_item);
    `uvm_object_utils(apb_raw_write_seq)
    bit [7:0]  addr;
    bit [31:0] data;
    function new(string name = "apb_raw_write_seq"); super.new(name); endfunction
    task body();
      req = apb_item::type_id::create("req");
      start_item(req);
      req.write = 1; req.addr = addr; req.data = data;
      finish_item(req);
    endtask
  endclass
endpackage

5. Teoría: anatomía del modelo y proceso de instanciación

Un modelo RAL es un árbol de objetos: un bloque contiene registros, memorias, subbloques y mapas de direcciones; cada registro contiene campos. Todos son uvm_object, no componentes: se crean con la fábrica, pero no participan en las fases. Esta sección describe cada clase, cada argumento de configuración y el orden exacto en que se construye el modelo.

uvm_reg_fileAgrupación lógica de registros (por ejemplo, los de un canal)Registros y otros register files

5.3 Constructor y configuración de un registro

function new(string name = "ctrl_reg");
  super.new(name, 32, UVM_NO_COVERAGE);     // nombre, n_bits, cobertura
endfunction

reg.configure(blk_parent, regfile_parent = null, hdl_path = "");
reg.build();                                // crea y configura sus campos
  • n_bits es el tamaño del registro; puede ser mayor que el bus: el mapa lo dividirá en varios accesos.
  • has_coverage indica qué modelos de cobertura puede construir (UVM_NO_COVERAGE, UVM_CVR_REG_BITS, UVM_CVR_ADDR_MAP, UVM_CVR_FIELD_VALS, UVM_CVR_ALL).
  • build() es un método virtual del propio registro (no una fase): lo llama el bloque justo después de configure().
  • hdl_path en configure declara una ruta que cubre todo el registro; para registros repartidos en varias señales se usa add_hdl_path_slice().

5.4 Memorias

function new(string name = "buf_mem");
  super.new(name, 32, 32, "RW", UVM_NO_COVERAGE);   // nombre, nº de palabras, bits por palabra, acceso
endfunction

mem.configure(blk_parent, hdl_path = "");
  • Una memoria no tiene campos, ni valor deseado, ni espejo: cada acceso va siempre al DUT. Por eso no hay mirror, set ni update para memorias.
  • El acceso puede ser "RW" o "RO" (ROM).
  • El backdoor accede a la palabra i añadiendo [i] a la ruta HDL.
  • Para repartir zonas de memoria entre secuencias existe uvm_mem_mam (gestor de asignación).

5.5 El bloque y el mapa

El primer mapa creado se asigna automáticamente a default_map. Un bloque puede tener varios mapas (por ejemplo, uno para el bus del procesador y otro para un bus de depuración).

5.6 El proceso de instanciación, paso a paso

env::build_phase └─ rm = regmem_reg_block::type_id::create("rm") 1. crear el bloque (fábrica) └─ rm.build() 2. construir su contenido: ├─ CTRL = ctrl_reg::type_id::create("CTRL") a. crear cada registro ├─ CTRL.configure(this, null, "") b. asociarlo al bloque (y a su ruta HDL) ├─ CTRL.build() c. crear y configurar sus campos │ └─ EN = uvm_reg_field::type_id::create("EN") │ └─ EN.configure(this, 1, 0, "RW", ...) ├─ CTRL.add_hdl_path_slice("en_q", 0, 1) ... d. rutas HDL por trozos (backdoor) ├─ BUF.configure(this, "mem") e. memorias ├─ default_map = create_map(...) f. mapa de direcciones └─ default_map.add_reg(CTRL, 'h00, "RW") ... g. colocar registros y memorias └─ rm.set_hdl_path_root("tb_top.dut") 3. raíz de las rutas HDL └─ rm.lock_model() 4. cerrar el modelo └─ rm.reset() 5. espejo y deseado = valores de reset env::connect_phase └─ rm.default_map.set_sequencer(agt.sqr, adapter) 6. conectar el mapa al bus └─ predictor.map = ...; predictor.adapter = ...; 7. predictor explícito agt.mon.ap.connect(predictor.bus_in) └─ rm.default_map.set_auto_predict(0)
  • Por qué build() y no el constructor: la fábrica necesita constructores con firma fija (solo el nombre). La construcción del contenido se separa en build() para que cada nivel pueda sustituirse por override antes de construirse.
  • Por qué se declaran rand: los registros del bloque y los campos de cada registro se declaran rand para que rm.randomize() o rm.CTRL.randomize() aleatoricen sus valores deseados respetando las restricciones.
  • lock_model() cierra el modelo: calcula las direcciones de todos los mapas, detecta solapamientos y prepara las búsquedas por dirección (que usa el predictor). Después no se pueden añadir registros. Sin él, el predictor no encuentra los registros y las búsquedas por dirección fallan.
  • reset() pone espejo y deseado al valor de reset; conviene llamarlo al construir el modelo y cada vez que el DUT se resetea.
  • Quién construye el modelo: lo habitual es el env, salvo que el test ya haya pasado uno (por ejemplo, el de un nivel superior que contiene este bloque como subbloque).

6. Teoría: políticas de acceso y tipos de registros

Otras propiedades que afectan al comportamiento

  • Volátil: el hardware cambia el valor (estado, contadores, flags de interrupción). El espejo solo se actualiza al leer, y mirror(UVM_CHECK) no lo compara. Olvidar marcar un campo como volátil produce falsos errores.
  • Sin reset (has_reset = 0): valor indeterminado tras el reset; las pruebas de reset no lo comprueban.
  • No aleatorizable (is_rand = 0): randomize() no lo toca.
  • Derechos del mapa: un registro con campos RW puede ser "RO" desde un mapa concreto. Los derechos del mapa limitan lo que se intenta; la política del campo describe lo que hace el hardware.

8. Adaptador y predictor

El modelo habla en operaciones de registro (escribir 0x305 en la dirección 0x00); el agente habla en items APB. El adaptador traduce en ambos sentidos, y el predictor usa esa traducción para mantener el espejo al día con todo lo que pasa por el bus.

8.1 Teoría: el adaptador

Cuando una secuencia llama a rm.CTRL.write(...), el mapa calcula la dirección y divide el acceso si hace falta. Por cada acceso al bus construye una estructura uvm_reg_bus_op y llama a adapter.reg2bus() para obtener un item del bus, que lanza en el secuenciador del agente. Cuando el driver termina, llama a adapter.bus2reg() para recuperar el dato y el estado.

Campo de uvm_reg_bus_opSignificado
kindUVM_READ o UVM_WRITE
addrDirección de bus ya calculada por el mapa
dataDato a escribir o dato leído
n_bitsNúmero de bits del acceso

statusUVM_IS_OK, UVM_NOT_OK o UVM_HAS_X; lo rellena bus2reg

provides_responses1 si el driver devuelve una respuesta separada (put_response/item_done(rsp)); el mapa la esperará con get_response. 0 si el driver deja el resultado en el propio item

Importancia: el adaptador es el único código del RAL que depende del bus. Cambiar el periférico de APB a AXI solo requiere otro adaptador; el modelo y todas las secuencias de registros siguen igual. Un error en provides_responses es una causa clásica de bloqueo: si vale 1 pero el driver no envía respuestas, el mapa espera indefinidamente.

  endfunction

  // Bus -> modelo (lo usan el mapa, tras cada acceso, y el predictor)
  virtual function void bus2reg(uvm_sequence_item bus_item, ref uvm_reg_bus_op rw);
    apb_item item;
    if (!$cast(item, bus_item)) begin
      `uvm_fatal("ADAPT", "bus2reg recibió un item que no es apb_item")
      return;
    end
    rw.kind   = item.write ? UVM_WRITE : UVM_READ;
    rw.addr   = item.addr;
    rw.data   = item.data;
    rw.n_bits = 32;
    rw.byte_en = '1;
    rw.status = UVM_IS_OK;      // con PSLVERR: item.slverr ? UVM_NOT_OK : UVM_IS_OK
  endfunction
endclass

8.3 Teoría: el predictor

Después de cada acceso, el espejo debe reflejar el nuevo valor del DUT según la política de cada campo (escribir 1 en un campo W1C lo deja a 0; leer un campo RC lo borra). Ese cálculo se llama predicción, y UVM ofrece tres formas de hacerla:

ModoCómo funcionaVentajasLimitaciones
Implícito (set_auto_predict(1))El mapa predice al terminar cada acceso hecho a través del modeloNo necesita monitor ni predictor; útil para empezarNo ve los accesos que no pasan por el modelo: otros masters, secuencias crudas, el firmware de un procesador
Explícito (uvm_reg_predictor, recomendado)Un componente recibe del monitor cada transacción del bus, la traduce con bus2reg, busca el registro por dirección y prediceEl espejo refleja todo lo que realmente pasó por el bus, venga de donde vengaNecesita monitor y conexión; el espejo se actualiza cuando el monitor publica (al final de la transferencia)
PasivoSolo predictor explícito, sin secuenciador en el mapa (el entorno no inicia accesos)Permite comprobar registros en un entorno donde otro agente (un CPU) programa el DUTNo se pueden hacer accesos frontdoor desde el modelo

El predictor explícito hace, por cada transacción observada:

  1. adapter.bus2reg(tr, rw) para obtener dirección, dato y tipo.
  2. map.get_reg_by_offset(rw.addr) (o get_mem_by_offset) para encontrar el registro. Por eso hace falta lock_model().
  3. reg.do_predict(...) con UVM_PREDICT_WRITE o UVM_PREDICT_READ: cada campo calcula su nuevo espejo según su política.
  4. Publica la operación por su puerto reg_ap, por si un scoreboard de registros la necesita.

Importancia: sin predicción correcta, el espejo se desvía del DUT; mirror(UVM_CHECK) da falsos errores, update() escribe cuando no debe o deja de escribir cuando debe, y las secuencias que dependen de get_mirrored_value() toman decisiones equivocadas. No uses los dos modos a la vez: cada acceso se predeciría dos veces.

9. El backdoor

Un acceso por backdoor lee o escribe directamente el almacenamiento del DUT (los flip-flops o el array de memoria) a través de la jerarquía de la simulación, sin usar el bus. No consume tiempo de simulación ni ciclos de bus.

9.1 Teoría: cómo funciona

  • UVM incluye funciones DPI-C (uvm_hdl_read, uvm_hdl_deposit, uvm_hdl_force, uvm_hdl_release, uvm_hdl_check_path) que acceden a una señal a partir de su ruta como cadena de texto, usando la interfaz VPI del simulador.
  • Cada registro y memoria del modelo puede tener una o varias rutas HDL. La ruta completa se forma concatenando: raíz del bloque superior (set_hdl_path_root), rutas de los bloques intermedios (configure(parent, "u_sub")) y la ruta del registro (o de cada trozo).
  • Si un registro está repartido en varias señales, cada trozo se declara con add_hdl_path_slice(nombre, offset, tamaño); UVM lee o escribe cada trozo y monta el valor. Los bits sin trozo se leen como 0.
  • Las memorias tienen una sola ruta al array; UVM añade [índice] en cada acceso.
  • Se pueden definir varios conjuntos de rutas con distinto kind (por defecto "RTL"; por ejemplo, "GATES" para la netlist) y elegir con cuál se trabaja con set_default_hdl_path().

Por qué es importante

  • Velocidad: inicializar una memoria de un millón de palabras por el bus puede llevar horas de simulación; por backdoor es inmediato.
  • Aislamiento de errores: escribir por frontdoor y leer por backdoor (o al revés) separa un fallo en el camino de escritura de un fallo en el de lectura.
  • Acceso a lo que el bus no alcanza: preparar estados difíciles de provocar, o leer campos sin efectos secundarios (leer un campo RC por backdoor con peek no lo borra).
  • Comprobación de rutas: las propias rutas HDL validan que el modelo y el RTL describen lo mismo.

Limitaciones: el backdoor no comprueba la lógica del bus ni la decodificación de direcciones; una escritura por backdoor no dispara los efectos secundarios que el hardware asocia a un acceso real (en CMD, escribir por backdoor no lanzaría la operación); y depende de que los nombres internos del RTL no cambien, sobre todo tras síntesis.

9.2 Dos formas de escribir por backdoor

OperaciónRespeta la política de accesoEjemplo con un campo W1C que vale 1
write(..., UVM_BACKDOOR) / read(..., UVM_BACKDOOR)Sí: UVM emula el efecto que tendría un acceso por el bus (lee, aplica la política, deposita)Escribir 1 deja el campo a 0, como haría el hardware
poke() / peek()No: escribe o lee el valor crudoEscribir 1 lo deja a 1; leer no tiene efectos secundarios

9.3 Implementación con rutas HDL

Las rutas ya están en el modelo (Sección 7.2) y la raíz en el env (rm.set_hdl_path_root("tb_top.dut")). Lo que falta es compilar dando acceso de lectura y escritura a la jerarquía:

SimuladorOpciones típicas

VCS-debug_access+all (o, más restringido, -debug_access+r+w)

Además, UVM no debe compilarse con UVM_HDL_NO_DPI definido, y los registros más anchos que UVM_HDL_MAX_WIDTH (1024 por defecto) necesitan redefinirlo. Si falta el acceso, verás errores de UVM indicando que no puede leer o depositar en la ruta, y las lecturas por backdoor devolverán 0.

Comprobar las rutas

UVM trae una secuencia que verifica que todas las rutas HDL del modelo existen:

Ejecútala siempre al integrar un modelo nuevo; una errata en una ruta aparecerá como error aquí en lugar de como un fallo misterioso más tarde.

9.4 Implementación de un backdoor de usuario

Cuando no se puede usar DPI (por política del proyecto, por rendimiento o porque el almacenamiento no es una señal simple, como un registro codificado o una memoria con ECC), se escribe una clase derivada de uvm_reg_backdoor que accede al DUT por referencias jerárquicas de SystemVerilog. El truco es declararla dentro de un módulo: las clases declaradas en un módulo pueden usar referencias jerárquicas, cosa que las clases de un paquete no pueden.

Añade a tb_top.sv, dentro del módulo y antes del bloque initial:

  // Backdoor de usuario para SCRATCH, por referencia jerárquica
  class scratch_bkdr extends uvm_reg_backdoor;
    function new(string name = "scratch_bkdr"); super.new(name); endfunction

    virtual task write(uvm_reg_item rw);
      do_pre_write(rw);                          // callbacks de usuario
      dut.scratch_q = rw.value[0][31:0];
      rw.status = UVM_IS_OK;
      `uvm_info("BKDR", $sformatf("write SCRATCH = 0x%08h", rw.value[0]), UVM_HIGH)
      do_post_write(rw);
    endtask

    virtual task read(uvm_reg_item rw);
      do_pre_read(rw);
      rw.value[0] = dut.scratch_q;
      rw.status   = UVM_IS_OK;
      `uvm_info("BKDR", $sformatf("read SCRATCH = 0x%08h", rw.value[0]), UVM_HIGH)
      do_post_read(rw);
    endtask
  endclass

  scratch_bkdr bk_scratch = new("bk_scratch");

Y en el bloque initial, antes de run_test(), pásalo al env:

    uvm_config_db #(uvm_reg_backdoor)::set(null, "uvm_test_top.env", "scratch_bkdr", bk_scratch);

En regmem_env::connect_phase, asígnalo al registro si existe:

      begin
        uvm_reg_backdoor bk;
        if (uvm_config_db #(uvm_reg_backdoor)::get(this, "", "scratch_bkdr", bk))
          rm.SCRATCH.set_backdoor(bk);
      end
  • Un backdoor de usuario tiene prioridad sobre las rutas HDL del registro. También se puede asignar a un bloque entero o a una memoria (uvm_mem::set_backdoor).
  • rw.value es un array dinámico porque las memorias pueden acceder a varias palabras (ráfagas); para un registro se usa rw.value[0].
  • do_pre_*/do_post_* ejecutan los callbacks del backdoor (por ejemplo, encode/decode para una memoria con ECC o cifrada).
  • Un backdoor también puede detectar cambios del hardware: sobrescribiendo is_auto_updated() y wait_for_change(), el modelo actualiza el espejo de campos volátiles automáticamente cuando la señal cambia.

Con +UVM_VERBOSITY=UVM_HIGH, los accesos por backdoor a SCRATCH mostrarán los mensajes BKDR, prueba de que se usa tu clase y no el DPI.

  endclass

Qué observar. MODE.write genera una escritura APB del registro completo, 0x00000307: UVM avisa de que el campo no es accesible individualmente y escribe el registro entero, tomando el resto de campos del espejo. Leer un campo también lee el registro completo y extrae el campo (0x03). Por eso un espejo incorrecto puede corromper otros campos al escribir uno solo: otra razón para tener buena predicción.

Paso 6: políticas de acceso en acción

  class step6_seq extends regmem_base_seq;
    `uvm_object_utils(step6_seq)
    function new(string name = "step6_seq"); super.new(name); endfunction
    task body();
      // Habilitar y lanzar una operación válida
      rm.CTRL.write(status, 32'h0000_0101, .parent(this));
      rm.CMD.write (status, 32'h1, .parent(this));
      // Sondear BUSY (campo RO volátil)
      do rm.STATUS.read(status, value, .parent(this));
      while (value[0]);
      `uvm_info("STEP6", $sformatf("STATUS = 0x%08h (DONE=%0d)", value, value[1]), UVM_LOW)

      // Flag de interrupción y borrado W1C
      rm.INT_STAT.read(status, value, .parent(this));
      `uvm_info("STEP6", $sformatf("INT_STAT = 0x%0h", value), UVM_LOW)
      rm.INT_STAT.write(status, 32'h1, .parent(this));
      `uvm_info("STEP6", $sformatf("Espejo INT_STAT tras W1C = 0x%0h", rm.INT_STAT.get_mirrored_value()), UVM_LOW)
      rm.INT_STAT.read(status, value, .parent(this));
      `uvm_info("STEP6", $sformatf("INT_STAT leído = 0x%0h", value), UVM_LOW)

      // Comando inválido: contador de errores
      rm.CMD.write(status, 32'hF, .parent(this));
      rm.STATUS.read(status, value, .parent(this));
      `uvm_info("STEP6", $sformatf("ERR_CNT = %0d", rm.STATUS.ERR_CNT.get_mirrored_value()), UVM_LOW)

      // Leer un registro WO y comprobar una constante
      rm.CMD.read(status, value, .parent(this));
      `uvm_info("STEP6", $sformatf("CMD leído = 0x%0h, espejo = 0x%0h", value, rm.CMD.get_mirrored_value()), UVM_LOW)
      rm.ID.mirror(status, UVM_CHECK, .parent(this));
    endtask
  endclass

Qué observar.

  • El sondeo lee STATUS una o dos veces con BUSY = 1 y termina con STATUS = 0x00000002 (DONE = 1).
  • INT_STAT vale 0x1. Tras escribir 1, el predictor aplica W1C y el espejo queda en 0; la lectura confirma 0.
  • Tras el comando 0xF, ERR_CNT = 1 (el espejo de un campo volátil se actualiza al leerlo).
  • Al leer CMD, el DUT devuelve 0 y el espejo conserva 0xF (lo último escrito): la predicción de lectura no modifica un campo WO. UVM puede avisar de que se está leyendo un campo de solo escritura.
  • El mirror(UVM_CHECK) de ID pasa: el valor de reset del modelo coincide con la constante del DUT.
  • Reflexión: un mirror(UVM_CHECK) sobre STATUS o INT_STAT no comprobaría nada, porque sus campos son volátiles. Para comprobarlos, lee el valor y compáralo con lo que esperas según la operación.

Paso 7: memoria por frontdoor y backdoor

  class step7_seq extends regmem_base_seq;
    `uvm_object_utils(step7_seq)
    function new(string name = "step7_seq"); super.new(name); endfunction
    task body();
      uvm_reg_data_t wr_data[] = '{32'h0000_0010, 32'h0000_0020, 32'h0000_0030, 32'h0000_0040};
      uvm_reg_data_t rd_data[];

      // a) Escritura frontdoor, lectura backdoor
      rm.BUF.write(status, 5, 32'h1111_2222, .parent(this));
      rm.BUF.read (status, 5, value, UVM_BACKDOOR, .parent(this));
      `uvm_info("STEP7", $sformatf("a) BUF[5] por backdoor = 0x%08h", value), UVM_LOW)

      // b) poke y lectura frontdoor
      rm.BUF.poke(status, 6, 32'hDEAD_BEEF, .parent(this));
      rm.BUF.read(status, 6, value, .parent(this));
      `uvm_info("STEP7", $sformatf("b) BUF[6] por frontdoor = 0x%08h", value), UVM_LOW)

      // c) Ráfagas
      rm.BUF.burst_write(status, 8, wr_data, .parent(this));
      rm.BUF.burst_read (status, 8, rd_data, .parent(this));
      foreach (rd_data[i])
        `uvm_info("STEP7", $sformatf("c) BUF[%0d] = 0x%08h", 8 + i, rd_data[i]), UVM_LOW)

      // d) Inicializar toda la memoria por backdoor (instantáneo)
      for (int i = 0; i < rm.BUF.get_size(); i++)
        rm.BUF.poke(status, i, 32'hA000_0000 + i, .parent(this));
      rm.BUF.read(status, 31, value, .parent(this));
      `uvm_info("STEP7", $sformatf("d) BUF[31] = 0x%08h", value), UVM_LOW)
    endtask
  endclass

Qué observar.

  • a) Una escritura APB a la dirección 0x94 (0x80 + 5·4) y la lectura por backdoor devuelve 0x11112222.
  • b) Una lectura APB en 0x98 que devuelve 0xDEADBEEF.
  • c) Como el adaptador no admite ráfagas, el mapa divide cada ráfaga en cuatro accesos sencillos a 0xA0, 0xA4, 0xA8 y 0xAC.
  • d) Las 32 escrituras ocurren en tiempo cero sin tráfico; solo aparece la lectura final, que devuelve 0xA000001F.
  • Recuerda: las memorias no tienen espejo; no existen mirror, set ni update para ellas. Si necesitas un modelo de referencia del contenido, mantenlo en el scoreboard.

Paso 8: aislar un error con frontdoor y backdoor

Compila con +define+BUG_SCRATCH: el DUT pierde el bit 31 al escribir SCRATCH.

  class step8_seq extends regmem_base_seq;
    `uvm_object_utils(step8_seq)
    function new(string name = "step8_seq"); super.new(name); endfunction
    task body();
      uvm_reg_data_t fd, bd;
      // Prueba 1: escribir por el bus, mirar el almacenamiento
      rm.SCRATCH.write(status, 32'h8000_0001, .parent(this));
      rm.SCRATCH.peek(status, bd, .parent(this));
      // Prueba 2: escribir el almacenamiento, leer por el bus
      rm.SCRATCH.poke(status, 32'h8000_0001, .parent(this));
      rm.SCRATCH.read(status, fd, .parent(this));
      `uvm_info("STEP8", $sformatf("write bus -> peek = 0x%08h | poke -> read bus = 0x%08h", bd, fd), UVM_LOW)
      if (bd != 32'h8000_0001 && fd == 32'h8000_0001)
        `uvm_error("STEP8", "Fallo en el camino de ESCRITURA del bus")
      else if (bd == 32'h8000_0001 && fd != 32'h8000_0001)
        `uvm_error("STEP8", "Fallo en el camino de LECTURA del bus")
    endtask
  endclass

Qué observar. Con el error inyectado, peek devuelve 0x00000001 y la lectura por bus devuelve 0x80000001: la secuencia diagnostica un fallo en el camino de escritura. Sin el error, ambos valen 0x80000001 y no hay mensaje. Con solo frontdoor habrías sabido que algo falla; con frontdoor y backdoor sabes dónde.

Paso 9: predict y reset del modelo

  class step9_seq extends regmem_base_seq;
    `uvm_object_utils(step9_seq)
    function new(string name = "step9_seq"); super.new(name); endfunction
    task body();
      // predict(): informar al modelo de un cambio conocido sin acceder al DUT
      void'(uvm_hdl_deposit("tb_top.dut.scratch_q", 32'h0000_BEEF));
      void'(rm.SCRATCH.predict(32'h0000_BEEF));
      rm.SCRATCH.mirror(status, UVM_CHECK, .parent(this));   // pasa: el modelo ya lo sabía

      // reset(): tras un reset del DUT, el modelo debe volver a los valores de reset
      rm.CTRL.write(status, 32'h0000_0F0F, .parent(this));
      rm.reset();
      `uvm_info("STEP9", $sformatf("Espejo de CTRL tras rm.reset() = 0x%08h", rm.CTRL.get_mirrored_value()), UVM_LOW)
      rm.CTRL.mirror(status, UVM_CHECK, .parent(this));      // falla: el DUT no se ha reseteado
    endtask
  endclass

Qué observar. El primer mirror pasa gracias a predict(). Tras rm.reset(), el espejo de CTRL vuelve a 0x00000100, pero el DUT sigue en 0x00000F0F, así que el segundo mirror informa un error. rm.reset() solo cambia el modelo; en un entorno real se llama cuando el monitor detecta que el DUT se ha reseteado.

Las exclusiones se declaran con el resource database, usando como ámbito "REG::" más el nombre completo del registro o memoria. Excluye los registros cuyos efectos secundarios rompen la prueba:

class builtin_test extends ral_test;
  `uvm_component_utils(builtin_test)
  function new(string name, uvm_component parent); super.new(name, parent); endfunction

  task run_phase(uvm_phase phase);
    uvm_reg_hw_reset_seq      rst_seq  = uvm_reg_hw_reset_seq::type_id::create("rst_seq");
    uvm_reg_bit_bash_seq      bash_seq = uvm_reg_bit_bash_seq::type_id::create("bash_seq");
    uvm_mem_walk_seq          walk_seq = uvm_mem_walk_seq::type_id::create("walk_seq");
    uvm_reg_mem_hdl_paths_seq path_seq = uvm_reg_mem_hdl_paths_seq::type_id::create("path_seq");

    // CMD lanza operaciones; STATUS e INT_STAT cambian por hardware
    uvm_resource_db #(bit)::set({"REG::", env.rm.CMD.get_full_name()},      "NO_REG_BIT_BASH_TEST", 1, this);
    uvm_resource_db #(bit)::set({"REG::", env.rm.STATUS.get_full_name()},   "NO_REG_BIT_BASH_TEST", 1, this);
    uvm_resource_db #(bit)::set({"REG::", env.rm.INT_STAT.get_full_name()}, "NO_REG_BIT_BASH_TEST", 1, this);

    phase.raise_objection(this);
    path_seq.model = env.rm;  path_seq.start(null);
    rst_seq.model  = env.rm;  rst_seq.start(null);
    bash_seq.model = env.rm;  bash_seq.start(null);
    walk_seq.model = env.rm;  walk_seq.start(null);
    phase.drop_objection(this);
  endtask
endclass

Qué observar. Sin errores inyectados, las cuatro secuencias terminan sin UVM_ERROR; el bit bash genera muchas transacciones (dos escrituras y dos lecturas por bit de CTRL y SCRATCH), y el walk de memoria, varias por palabra. Repite con +define+BUG_SCRATCH: el bit bash informa del bit 31 de SCRATCH sin que hayas escrito ninguna prueba específica.

Ejercicio: ¿por qué hay que excluir CMD del bit bash?

El bit bash escribe patrones en cada registro. En CMD, con EN a 1, escribir valores distintos de 0 lanza operaciones o incrementa ERR_CNT, cambiando STATUS e INT_STAT en mitad de la prueba. Además, un campo WO no puede leerse para comprobar lo escrito. Cualquier registro con efectos secundarios al escribirse debe excluirse o probarse con secuencias específicas.

13. Evaluación y referencias

13.1 Preguntas

  1. Explica la diferencia entre valor deseado, espejo y real.
  2. ¿Por qué el contenido de un registro se crea en build() y no en el constructor?
  3. ¿Qué hace lock_model() y qué falla si se omite?
  4. Un campo de estado cambia por hardware. ¿Qué argumento de configure debes poner a 1 y qué consecuencia tiene?
  5. ¿Qué diferencia hay entre las políticas W1C, WC y RC?
  6. ¿Qué devuelve reg2bus y cuándo llama UVM a bus2reg?
  7. ¿Por qué se prefiere el predictor explícito al implícito?
  8. ¿Qué diferencia hay entre write(..., UVM_BACKDOOR) y poke() en un campo W1C?
  9. ¿Por qué una clase de backdoor de usuario se declara dentro de un módulo?
  10. ¿Por qué no existe mirror() para memorias?
13.2 Respuestas
  1. El deseado es el valor que queremos que tenga el registro (lo cambian set y randomize); el espejo es lo que el modelo cree que tiene el DUT (lo actualizan las predicciones); el real es lo que hay en el DUT.
  2. Porque la fábrica necesita constructores con firma fija; separar la construcción permite sustituir cada clase por override y configurar antes de construir.
  3. Cierra el modelo: calcula direcciones, detecta solapamientos y prepara las búsquedas por dirección. Sin él, el predictor no encuentra registros por dirección y los accesos dan errores.
  4. volatile. El espejo solo se actualiza al leer, y mirror(UVM_CHECK) no compara ese campo.
  5. W1C: cada 1 escrito borra su bit. WC: cualquier escritura borra todo el campo. RC: la lectura borra todo el campo.
  6. reg2bus devuelve el item del bus a partir de la operación de registro. UVM llama a bus2reg al terminar cada acceso frontdoor (para recuperar dato y estado) y el predictor lo llama con cada transacción observada.
  7. Porque ve todo lo que ocurre en el bus, incluidos accesos de otros masters y secuencias que no usan el modelo; el implícito solo conoce los accesos hechos a través del modelo.
  8. write por backdoor emula la política: escribir 1 borra el bit. poke escribe el valor crudo: escribir 1 lo deja a 1.
  9. Porque las clases declaradas en un módulo pueden usar referencias jerárquicas a señales del diseño; las de un paquete no.
  10. Porque las memorias no tienen espejo: guardar una copia de memorias grandes sería costoso, así que cada acceso va siempre al DUT. Si se necesita un modelo de contenido, se mantiene en el scoreboard.

13.3 Ampliaciones propuestas

  • Añade un campo LOCK de política W1 a CTRL (en el modelo y en el RTL) y comprueba con el bit bash cómo lo trata UVM.
  • Añade al DUT PSLVERR para direcciones no mapeadas y propaga el error en bus2reg como UVM_NOT_OK.
  • Activa cobertura (UVM_CVR_FIELD_VALS) en CTRL y mide qué valores de MODE se han escrito.
  • Genera el modelo desde una descripción IP-XACT o SystemRDL con un generador y compáralo con el escrito a mano.
