TeoríaT1. ¿Por qué UVM?

Un testbench tradicional en Verilog suele ser un único módulo con estímulos escritos a mano y comparaciones visuales en formas de onda. Ese enfoque no escala: cuando el diseño crece, los casos de prueba se multiplican y cada nuevo proyecto empieza casi desde cero.

La Universal Verification Methodology (UVM) es una biblioteca de clases de SystemVerilog, estandarizada como IEEE 1800.2, que define cómo organizar un testbench para que sea:

  • Por capas: el estímulo se describe como transacciones abstractas (p. ej. “escribir el dato 0xAB en la dirección 0x10”), y solo el driver sabe convertirlas en señales.
  • Aleatorio con restricciones (CRV): en lugar de escribir cada caso, se describen las reglas y el simulador genera miles de combinaciones.
  • Autoverificable: un scoreboard compara automáticamente la salida contra lo esperado; nadie revisa ondas a mano.
  • Reutilizable: un agente para un protocolo (p. ej. AXI) se reutiliza en cualquier proyecto que use ese protocolo.
  • Configurable sin editar código: gracias a la fábrica y a la base de datos de configuración, un test puede reemplazar componentes o cambiar parámetros.
Idea clave Separar qué se prueba (secuencias y tests) de cómo se aplica al hardware (driver/monitor) y de cómo se decide si está bien (scoreboard).

TeoríaT3. Objetos y componentes

Todas las clases UVM heredan de uvm_object. De ahí se ramifican dos familias con comportamientos muy distintos:

¿Por qué importa el parent? Al crear un componente se le pasa this como padre. Así UVM construye el árbol jerárquico, que se usa para nombrar componentes, ejecutar las fases en orden y resolver las rutas de uvm_config_db (por ejemplo "e0.a0.*").

TeoríaT4. La fábrica (factory) y las macros de utilidad

En todo el ejemplo los objetos se crean así:

d0 = driver::type_id::create("d0", this);     // en lugar de  d0 = new("d0", this);

type_id::create() pide el objeto a la fábrica de UVM. La ventaja es que un test puede ordenar “cada vez que alguien pida un driver, entrégale un driver_con_errores” (un override) sin modificar el agente:

driver::type_id::set_type_override(driver_con_errores::get_type());

Para que una clase pueda crearse con la fábrica debe estar registrada, y eso hacen las macros:

  • `uvm_component_utils(driver) — registra un componente.
  • `uvm_object_utils(gen_item_seq) — registra un objeto.
  • `uvm_object_utils_begin(switch_item) … `uvm_field_int(addr, UVM_DEFAULT) … `uvm_object_utils_end — registra el objeto y además genera automáticamente print(), copy(), compare(), clone(), etc. para los campos listados. UVM_DEFAULT activa todas esas operaciones para el campo.
Regla práctica Use siempre type_id::create para componentes y transacciones. El monitor del ejemplo usa switch_item item = new;, lo cual funciona, pero impide aplicar overrides de fábrica a ese objeto.

TeoríaT5. Las fases de UVM

Los componentes no tienen un “main”. En su lugar, UVM llama a métodos predefinidos (fases) en un orden fijo, sincronizado en todo el árbol. Basta con sobrescribir los que se necesiten:

build_phase ↓connect_phase ↑end_of_elaboration_phasestart_of_simulation_phase run_phase (task, consume tiempo) extract_phasecheck_phasereport_phasefinal_phase
FaseTipoUso en el ejemplo
build_phasefunction, de arriba hacia abajoCrear los hijos (type_id::create) y obtener configuración (uvm_config_db::get). Va de arriba hacia abajo porque un padre debe existir antes de crear a sus hijos.
connect_phasefunction, de abajo hacia arribaConectar puertos TLM: driver↔sequencer en el agente; monitor→scoreboard en el ambiente.
end_of_elaboration_phasefunctionAjustes finales; aquí imprimimos la topología.
run_phasetask (consume tiempo)Se ejecuta en paralelo en todos los componentes: el driver maneja pines, el monitor observa, el test arranca la secuencia.
report_phasefunctionImprimir resúmenes (lo añadimos al scoreboard).
Siempre llame a super.xxx_phase(phase) Es una buena práctica que verá en todo el código; algunas clases base realizan trabajo (p. ej. configuración automática de campos) en su implementación.

run_test("test"), llamado desde tb_top, crea el test con la fábrica (con el nombre de instancia uvm_test_top) y dispara todas las fases. El argumento +UVM_TESTNAME=... en la línea de comandos tiene prioridad, lo que permite elegir el test sin recompilar.

TeoríaT6. Interfaces virtuales y uvm_config_db

El DUT y la interface son elementos estáticos (existen desde la elaboración). Las clases son dinámicas (se crean en tiempo de ejecución) y no pueden contener una interfaz directamente. La solución es la interfaz virtual: un handle (puntero) a una instancia de interfaz.

virtual switch_if vif;     // handle; vif.addr accede a la señal real

¿Cómo llega ese handle desde el módulo hasta el driver? Mediante uvm_config_db, una base de datos global indexada por ruta jerárquica + nombre:

// set(contexto, ruta_relativa, nombre, valor)
uvm_config_db#(virtual switch_if)::set(null, "uvm_test_top", "switch_vif", _if);   // tb_top
uvm_config_db#(virtual switch_if)::set(this, "e0.a0.*",     "switch_vif", vif);   // test
// get(contexto, ruta_relativa, nombre, variable_destino) devuelve 1 si lo encontró
uvm_config_db#(virtual switch_if)::get(this, "", "switch_vif", vif);                // driver/monitor

Flujo en el ejemplo:

  1. tb_top publica la interfaz para uvm_test_top (el test).
  2. El test la obtiene y la vuelve a publicar para todo lo que esté debajo de uvm_test_top.e0.a0 (el comodín * incluye a d0 y m0).
  3. Driver y monitor la obtienen en su build_phase. Si no la encuentran, `uvm_fatal detiene la simulación con un mensaje claro.
El tipo, el nombre y la ruta deben coincidir exactamente. Un set con "switch_vif" y un get con "switch_if" producen el fatal “Could not get vif”. Es el error más común en un primer ambiente UVM.

TeoríaT7. Comunicación TLM

Los componentes no se llaman directamente entre sí; se comunican por puertos TLM (Transaction Level Modeling). Así un componente no necesita saber quién está del otro lado, lo que favorece la reutilización. En el ejemplo hay dos conexiones:

a) Sequencer → Driver (bidireccional, “pull”)

El driver tiene seq_item_port y el sequencer seq_item_export. Se conectan en el agente:

d0.seq_item_port.connect(s0.seq_item_export);

El driver pide transacciones con get_next_item() y avisa que terminó con item_done().

b) Monitor → Scoreboard (unidireccional, difusión)

El monitor tiene un uvm_analysis_port; el scoreboard un uvm_analysis_imp. Se conectan en el ambiente:

a0.m0.mon_analysis_port.connect(sb0.m_analysis_imp);

Cuando el monitor llama mon_analysis_port.write(item), UVM llama inmediatamente a la función write(item) del scoreboard. Un analysis port puede conectarse a varios receptores (scoreboard, cobertura, etc.) y funciona aunque no haya ninguno conectado.

¿Por qué uvm_analysis_imp #(switch_item, scoreboard) lleva dos parámetros? El segundo parámetro indica la clase que implementa la función write(). Por eso el scoreboard debe definir function void write(switch_item item) con exactamente esa firma.

TeoríaT8. Secuencias, sequencer y el “handshake”

Una secuencia es un uvm_object cuyo método body() genera transacciones. Se ejecuta sobre un sequencer con seq.start(e0.a0.s0). El intercambio entre secuencia, sequencer y driver es:

  • Aleatorizar después de start_item (paso 4) permite “aleatorización tardía”: el item se genera justo cuando el driver lo va a usar.
  • finish_item no retorna hasta que el driver llama item_done: la secuencia avanza al ritmo del DUT.
  • La macro `uvm_do(item) que aparece en la presentación es un atajo de create + start_item + randomize + finish_item. Es cómoda pero oculta el proceso; en este laboratorio usamos la forma explícita.

TeoríaT9. Objeciones: ¿cuándo termina la simulación?

El driver y el monitor contienen lazos forever: nunca terminan por sí mismos. UVM usa objeciones para decidir cuándo finalizar la run_phase:

phase.raise_objection(this);   // "no terminen todavía, estoy trabajando"
...                             // reset + secuencia
phase.drop_objection(this);    // "ya terminé"

Cuando el contador de objeciones vuelve a cero, UVM termina la run_phase (matando los lazos forever) y continúa con extract, check, report y final.

Errores típicos
  • No levantar ninguna objeción ⇒ la simulación termina en el tiempo 0 sin hacer nada.
  • Bajarla demasiado pronto ⇒ la última transacción no llega al scoreboard. Por eso añadimos repeat(5) @(posedge vif.clk) antes de drop_objection (la segunda prueba de la presentación usa #200 con el mismo propósito).

El ID (por ejemplo "DRV", "SCBD") permite filtrar el log con grep. Al final de la simulación UVM imprime el UVM Report Summary con el número de mensajes de cada severidad: un test pasa si tiene 0 UVM_ERROR y 0 UVM_FATAL.

TeoríaT11. Aleatorización con restricciones

  • rand bit [7:0] addr; — el campo recibe un valor aleatorio cada vez que se llama obj.randomize(). Los campos sin rand (p. ej. addr_a) no cambian: son respuestas que llena el monitor.
  • constraint c1 { num inside {[2:5]}; } — limita los valores posibles (aquí, entre 2 y 5 transacciones).
  • randomize() devuelve 1 si encontró una solución y 0 si las restricciones son contradictorias. Siempre verifique el valor de retorno; si se ignora, VCS emite una advertencia y un fallo pasaría desapercibido.
  • seq.randomize() with { num inside {[20:30]}; } — agrega restricciones en línea desde el test.
  • soft — una restricción blanda cede ante otra que la contradiga. En la Parte 2, la secuencia tiene soft num inside {[2:5]} y el test pide [20:30]: sin soft la aleatorización fallaría.
  • La semilla se controla en VCS con +ntb_random_seed=N. Misma semilla ⇒ misma simulación (reproducible).

TeoríaT12. Temporización en SystemVerilog (para entender driver y monitor)

Asignación no bloqueante (<=) y regiones de evaluación

En cada flanco de reloj el simulador primero ejecuta todo el código activo (lecturas, @(posedge clk) que despiertan, etc.) y solo después actualiza las variables asignadas con <= (región NBA). Consecuencias:

  • Cuando el driver escribe vif.vld <= 1 justo después de un flanco, el DUT y el monitor ven el nuevo valor en el siguiente flanco. No hay carrera.
  • En el driver, vif.vld <= 0 seguido (en el mismo instante) por vif.vld <= 1 de la siguiente transacción deja vld = 1: la última asignación NBA gana. Por eso transacciones consecutivas salen una por ciclo, sin huecos.
  • Cuando el monitor lee vif.addr_a en un flanco, lee el valor antes de que el DUT lo actualice en ese mismo flanco.

fork … join

Lanza varios procesos en paralelo. join espera a que todos terminen (con lazos forever, nunca terminan; los detiene el fin de la run_phase).

Semáforos

semaphore sema4 = new(1); crea un semáforo con 1 llave. get() toma la llave (bloquea si no hay), put() la devuelve. En el monitor del switch garantiza que solo un hilo a la vez esté capturando la parte de “entrada” de una transacción.

Clases y handles

switch_item item = new; crea un objeto nuevo. Es importante crear un objeto nuevo por cada transacción en el monitor: si se reutilizara el mismo, el scoreboard podría recibir un handle cuyo contenido cambia después.

Parte 1P2. El DUT: un switch sencillo

El switch recibe un paquete (addr, data) cuando vld = 1 y lo envía, un ciclo después, a uno de dos puertos:

  • Puerto A (addr_a, data_a) si 0 ≤ addr ≤ ADDR_DIV (0x3F por defecto). El puerto B se pone en 0.
  • Puerto B (addr_b, data_b) en caso contrario. El puerto A se pone en 0.
  • Con rstn = 0 (reset activo en bajo, síncrono) todas las salidas van a 0. Si vld = 0 las salidas mantienen su valor.
switch/switch.sv
// =====================================================================
// DUT: switch sencillo (tomado de la presentación)
// Si la dirección está en [0 : ADDR_DIV] el paquete sale por el puerto A,
// en caso contrario sale por el puerto B. Latencia: 1 ciclo de reloj.
// =====================================================================
module switch
  # (parameter ADDR_WIDTH = 8,
     parameter DATA_WIDTH = 16,
     parameter ADDR_DIV   = 8'h3F
    )
  ( input                         clk,
    input                         rstn,
    input                         vld,

    input      [ADDR_WIDTH-1:0]   addr,
    input      [DATA_WIDTH-1:0]   data,

    output reg [ADDR_WIDTH-1:0]   addr_a,
    output reg [DATA_WIDTH-1:0]   data_a,

    output reg [ADDR_WIDTH-1:0]   addr_b,
    output reg [DATA_WIDTH-1:0]   data_b
  );

  always @ (posedge clk) begin
    if (!rstn) begin
      addr_a <= 0;
      data_a <= 0;
      addr_b <= 0;
      data_b <= 0;
    end else begin
      if (vld) begin
        if (addr >= 0 & addr <= ADDR_DIV) begin
          addr_a <= addr;
          data_a <= data;
          addr_b <= 0;
          data_b <= 0;
        end else begin
          addr_a <= 0;
          data_a <= 0;
          addr_b <= addr;
          data_b <= data;
        end
      end
    end
  end
endmodule

Parte 1P3. La interfaz

La presentación no muestra la interfaz, pero es indispensable. Contiene todas las señales del DUT excepto el reloj, que entra como puerto para que la interfaz y el DUT compartan el mismo reloj. Se usan señales logic porque el driver las maneja desde código procedural (una clase).

switch/switch_if.sv
// =====================================================================
// Interfaz: agrupa todas las señales entre el testbench y el DUT.
// No aparece en la presentación, pero es obligatoria para compilar.
// =====================================================================
interface switch_if (input bit clk);
  logic        rstn;
  logic        vld;
  logic [7:0]  addr;
  logic [15:0] data;

  logic [7:0]  addr_a;
  logic [15:0] data_a;
  logic [7:0]  addr_b;
  logic [15:0] data_b;
endinterface
Para profundizar En ambientes más grandes se añaden clocking blocks y modport para definir con precisión cuándo se muestrean y manejan las señales. Aquí se omiten para mantener el código igual al de la presentación.

Parte 1P4. El sequence item (transacción)

Representa un paquete completo: lo que se envía (addr, data, aleatorios) y lo que el DUT devuelve en sus dos puertos (llenados por el monitor). Las macros de campo generan print(), que usaremos en la secuencia y el monitor.

switch/switch_item.sv
// This is the base transaction object that will be used
// in the environment to initiate new transactions and
// capture transactions at DUT interface
class switch_item extends uvm_sequence_item;
  rand bit [7:0]   addr;     // estímulo (aleatorio)
  rand bit [15:0]  data;     // estímulo (aleatorio)
  bit [7:0]        addr_a;   // respuesta observada en el puerto A
  bit [15:0]       data_a;
  bit [7:0]        addr_b;   // respuesta observada en el puerto B
  bit [15:0]       data_b;

  // Use utility macros to implement standard functions
  // like print, copy, clone, etc
  `uvm_object_utils_begin(switch_item)
    `uvm_field_int (addr,   UVM_DEFAULT)
    `uvm_field_int (data,   UVM_DEFAULT)
    `uvm_field_int (addr_a, UVM_DEFAULT)
    `uvm_field_int (data_a, UVM_DEFAULT)
    `uvm_field_int (addr_b, UVM_DEFAULT)
    `uvm_field_int (data_b, UVM_DEFAULT)
  `uvm_object_utils_end

  function new(string name = "switch_item");
    super.new(name);
  endfunction
endclass

Parte 1P5. La secuencia

Genera entre 2 y 5 transacciones aleatorias (variable num). Cada iteración sigue el handshake de la sección T8: create → start_item → randomize → finish_item.

switch/gen_item_seq.sv
// Secuencia: genera 'num' transacciones aleatorias de tipo switch_item.
// Nota: en la presentación se escribe "extends uvm_sequence;" (sin parámetro).
// Parametrizarla con #(switch_item) es la práctica recomendada: así REQ/RSP
// quedan tipados correctamente.
class gen_item_seq extends uvm_sequence #(switch_item);
  `uvm_object_utils(gen_item_seq)
  function new(string name="gen_item_seq");
    super.new(name);
  endfunction

  rand int num;     // Config total number of items to be sent

  constraint c1 { num inside {[2:5]}; }

  virtual task body();
    for (int i = 0; i < num; i ++) begin
      switch_item m_item = switch_item::type_id::create("m_item");
      start_item(m_item);
      if (!m_item.randomize())
        `uvm_error("SEQ", "Fallo al aleatorizar m_item")
      `uvm_info("SEQ", $sformatf("Generate new item: "), UVM_LOW)
      m_item.print();
      finish_item(m_item);
    end
    `uvm_info("SEQ", $sformatf("Done generation of %0d items", num), UVM_LOW)
  endtask
endclass
Diferencia con la presentación Se parametrizó como uvm_sequence #(switch_item) y se verifica el retorno de randomize(). El comportamiento es el mismo.

Parte 1P6. El driver

El driver extiende uvm_driver #(switch_item), que ya incluye el puerto seq_item_port. Su trabajo:

  1. build_phase: obtener la interfaz virtual de uvm_config_db.
  2. run_phase: en un lazo infinito, pedir un item, manejarlo sobre los pines y avisar que terminó.
  3. drive_item: poner vld = 1 con addr/data, esperar un flanco (el DUT captura el dato) y bajar vld.
switch/driver.sv
// Driver: recibe transacciones del sequencer y las convierte en
// actividad a nivel de pines sobre la interfaz virtual.
class driver extends uvm_driver #(switch_item);
  `uvm_component_utils(driver)
  function new(string name = "driver", uvm_component parent=null);
    super.new(name, parent);
  endfunction

  virtual switch_if vif;

  virtual function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    if (!uvm_config_db#(virtual switch_if)::get(this, "", "switch_vif", vif))
      `uvm_fatal("DRV", "Could not get vif")
  endfunction

  virtual task run_phase(uvm_phase phase);
    super.run_phase(phase);
    vif.vld <= 0;   // (añadido) valor inicial conocido en lugar de X
    forever begin
      switch_item m_item;
      `uvm_info("DRV", $sformatf("Wait for item from sequencer"), UVM_LOW)
      seq_item_port.get_next_item(m_item);
      drive_item(m_item);
      seq_item_port.item_done();
    end
  endtask

  virtual task drive_item(switch_item m_item);
    vif.vld  <= 1;
    vif.addr <= m_item.addr;
    vif.data <= m_item.data;

    @ (posedge vif.clk);
    vif.vld  <= 0;
  endtask
endclass

Parte 1P7. El monitor

El monitor es pasivo: nunca maneja señales. En cada flanco, si rstn y vld están en 1, captura addr/data (primera parte), espera un flanco más y captura las salidas (segunda parte). Luego envía el item completo por mon_analysis_port.

¿Por qué dos hilos? Mientras el hilo 0 espera la salida de la transacción N (segundo flanco), en ese mismo flanco puede aparecer la entrada de la transacción N+1. Un único hilo la perdería. Con dos hilos y el semáforo, un hilo atiende la transacción N y el otro la N+1, de forma alternada (pipeline de 2 etapas).

switch/monitor.sv
// Monitor: observa pasivamente la interfaz, reconstruye transacciones
// completas (entrada + salida) y las publica por un analysis port.
class monitor extends uvm_monitor;
  `uvm_component_utils(monitor)
  function new(string name="monitor", uvm_component parent=null);
    super.new(name, parent);
  endfunction

  uvm_analysis_port #(switch_item) mon_analysis_port;
  virtual switch_if vif;
  semaphore sema4;

  virtual function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    if (!uvm_config_db#(virtual switch_if)::get(this, "", "switch_vif", vif))
      `uvm_fatal("MON", "Could not get vif")
    sema4 = new(1);
    mon_analysis_port = new ("mon_analysis_port", this);
  endfunction

  virtual task run_phase(uvm_phase phase);
    super.run_phase(phase);
    // Dos hilos en paralelo: mientras uno espera la salida de la
    // transacción N, el otro ya puede capturar la entrada de la N+1.
    fork
      sample_port("Thread0");
      sample_port("Thread1");
    join
  endtask

  virtual task sample_port(string tag="");
    // This task monitors the interface for a complete
    // transaction and pushes into the mailbox when the
    // transaction is complete
    forever begin
      @(posedge vif.clk);
      if (vif.rstn & vif.vld) begin
        switch_item item = new;
        sema4.get();
        item.addr = vif.addr;
        item.data = vif.data;
        `uvm_info("MON", $sformatf("T=%0t [Monitor] %s First part over",
                                   $time, tag), UVM_LOW)
        @(posedge vif.clk);
        sema4.put();
        item.addr_a = vif.addr_a;
        item.data_a = vif.data_a;
        item.addr_b = vif.addr_b;
        item.data_b = vif.data_b;
        mon_analysis_port.write(item);
        `uvm_info("MON", $sformatf("T=%0t [Monitor] %s Second part over, item:",
                                   $time, tag), UVM_LOW)
        item.print();
      end
    end
  endtask
endclass

Parte 1P9. El scoreboard

Implementa write(), que se ejecuta cada vez que el monitor publica un item. Contiene el modelo de referencia del switch: si addr ≤ 0x3F, la transacción debe aparecer igual en el puerto A; si no, en el puerto B. Si no coincide, reporta `uvm_error.

switch/scoreboard.sv
// Scoreboard: compara lo observado contra el comportamiento esperado.
class scoreboard extends uvm_scoreboard;
  `uvm_component_utils(scoreboard)
  function new(string name="scoreboard", uvm_component parent=null);
    super.new(name, parent);
  endfunction

  uvm_analysis_imp #(switch_item, scoreboard) m_analysis_imp;

  int unsigned n_pass;   // (añadido) contadores para el resumen final
  int unsigned n_fail;

  virtual function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    m_analysis_imp = new("m_analysis_imp", this);
  endfunction

  // OJO: la presentación declara "virtual function write(...)" sin tipo de
  // retorno (implícitamente devuelve 1 bit). Debe ser "function void".
  virtual function void write(switch_item item);
    if (item.addr inside {[0:'h3f]}) begin
      if (item.addr_a != item.addr | item.data_a != item.data) begin
        `uvm_error("SCBD", $sformatf("ERROR! Mismatch addr=0x%0h data=0x%0h addr_a=0x%0h data_a=0x%0h",
                   item.addr, item.data, item.addr_a, item.data_a))
        n_fail++;
      end else begin
        `uvm_info("SCBD", $sformatf("PASS! Match addr=0x%0h data=0x%0h addr_a=0x%0h data_a=0x%0h",
                  item.addr, item.data, item.addr_a, item.data_a), UVM_LOW)
        n_pass++;
      end
    end else begin
      if (item.addr_b != item.addr | item.data_b != item.data) begin
        `uvm_error("SCBD", $sformatf("ERROR! Mismatch addr=0x%0h data=0x%0h addr_b=0x%0h data_b=0x%0h",
                   item.addr, item.data, item.addr_b, item.data_b))
        n_fail++;
      end else begin
        `uvm_info("SCBD", $sformatf("PASS! Match addr=0x%0h data=0x%0h addr_b=0x%0h data_b=0x%0h",
                  item.addr, item.data, item.addr_b, item.data_b), UVM_LOW)
        n_pass++;
      end
    end
  endfunction

  // (añadido) Resumen al final de la simulación
  virtual function void report_phase(uvm_phase phase);
    super.report_phase(phase);
    `uvm_info("SCBD", $sformatf("Resumen: %0d PASS, %0d FAIL", n_pass, n_fail), UVM_NONE)
  endfunction
endclass
Corrección importante respecto a la presentación En la presentación la función se declara como virtual function write(switch_item item);. Sin tipo de retorno, SystemVerilog asume que devuelve un valor de 1 bit, lo cual no coincide con la firma function void write(...) que espera uvm_analysis_imp. Debe declararse como virtual function void write(...).

Además se añadieron dos contadores y un report_phase que imprime el resumen PASS/FAIL al final.

Parte 1P11. El test

El test es la raíz del árbol de componentes. En build_phase crea el ambiente, obtiene la interfaz del tb_top y la redistribuye hacia el agente. En run_phase:

  1. Levanta una objeción.
  2. Aplica reset (5 ciclos en 0, luego 10 ciclos de espera).
  3. Aleatoriza la secuencia (elige num) y la arranca sobre el sequencer e0.a0.s0. start() bloquea hasta que body() termina.
  4. Espera unos ciclos para que la última transacción llegue al scoreboard y baja la objeción.
switch/test.sv
// Test: construye el ambiente, configura, aplica reset y arranca la secuencia.
class test extends uvm_test;
  `uvm_component_utils(test)
  function new(string name = "test", uvm_component parent=null);
    super.new(name, parent);
  endfunction

  env e0;
  virtual switch_if vif;

  virtual function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    e0 = env::type_id::create("e0", this);
    if (!uvm_config_db#(virtual switch_if)::get(this, "", "switch_vif", vif))
      `uvm_fatal("TEST", "Did not get vif")

    uvm_config_db#(virtual switch_if)::set(this, "e0.a0.*", "switch_vif", vif);
  endfunction

  // (añadido) Imprime la jerarquía de componentes construida
  virtual function void end_of_elaboration_phase(uvm_phase phase);
    super.end_of_elaboration_phase(phase);
    uvm_root::get().print_topology();
  endfunction

  virtual task run_phase(uvm_phase phase);
    gen_item_seq seq = gen_item_seq::type_id::create("seq");
    phase.raise_objection(this);
    apply_reset();

    if (!seq.randomize())
      `uvm_fatal("TEST", "Fallo al aleatorizar la secuencia")
    seq.start(e0.a0.s0);
    // (añadido) Unos ciclos extra para que el monitor capture la
    // salida de la última transacción antes de terminar la simulación.
    repeat (5) @(posedge vif.clk);
    phase.drop_objection(this);
  endtask

  virtual task apply_reset();
    vif.rstn <= 0;
    repeat(5)  @ (posedge vif.clk);
    vif.rstn <= 1;
    repeat(10) @ (posedge vif.clk);
  endtask
endclass

Parte 2R1. Segundo ejemplo: controlador de registros (reg_ctrl)

El segundo ejemplo de la presentación usa exactamente la misma arquitectura, pero con un DUT más interesante: una memoria de 256 registros de 16 bits con protocolo de lectura/escritura.

SeñalDirecciónFunción
selentradaIndica que hay una transacción válida.
wrentrada1 = escritura, 0 = lectura.
addr, wdataentradaDirección y dato a escribir.
rdatasalidaDato leído (disponible un ciclo después de la lectura).

Protocolo: una escritura se completa en un ciclo. Una lectura entrega rdata en el ciclo siguiente y baja ready; mientras ready = 0 no se puede iniciar otra transacción. Tras el reset, todos los registros valen RESET_VAL = 0x1234.

Conceptos nuevos de este ejemplo

  • Driver con control de flujo: después de presentar la transacción espera mientras ready = 0 (while (!vif.ready)). Así el driver respeta el protocolo del DUT.
  • Monitor que depende del tipo de transacción: para lecturas espera un ciclo adicional para capturar rdata. No necesita dos hilos (el semáforo quedó declarado pero no se usa).
  • Scoreboard con modelo de referencia con estado: el arreglo refq[`DEPTH] recuerda la última escritura a cada dirección. Una lectura se compara contra esa escritura, o contra 0x1234 si nunca se escribió.
  • convert2str(): función propia del item para imprimir una transacción en una sola línea.
  • Macros `define (`ADDR_WIDTH, `DATA_WIDTH, `DEPTH) compartidas por DUT, interfaz y clases; las colocamos en reg_defines.svh con protección contra inclusión doble.
  • Restricción soft en la secuencia, sobrescrita por el test con randomize() with {num inside {[20:30]};}.

// Note that in this protocol, write data is provided
// in a single clock along with the address while read
// data is received on the next clock, and no transactions
// can be started during that time indicated by "ready"
// signal.

module reg_ctrl
  # (
    parameter ADDR_WIDTH = 8,
    parameter DATA_WIDTH = 16,
    parameter DEPTH      = 256,
    parameter RESET_VAL  = 16'h1234
  )
  ( input                       clk,
    input                       rstn,
    input      [ADDR_WIDTH-1:0] addr,
    input                       sel,
    input                       wr,
    input      [DATA_WIDTH-1:0] wdata,
    output reg [DATA_WIDTH-1:0] rdata,
    output reg                  ready);

  // Some memory element to store data for each addr
  reg [DATA_WIDTH-1:0] ctrl [DEPTH];

  reg  ready_dly;
  wire ready_pe;

  // If reset is asserted, clear the memory element
  // Else store data to addr for valid writes
  // For reads, provide read data back
  always @ (posedge clk) begin
    if (!rstn) begin
      for (int i = 0; i < DEPTH; i += 1) begin
        ctrl[i] <= RESET_VAL;
      end
    end else begin
      if (sel & ready & wr) begin
        ctrl[addr] <= wdata;
      end

      if (sel & ready & !wr) begin
        rdata <= ctrl[addr];
      end else begin
        rdata <= 0;
      end
    end
  end

  // Ready is driven using this always block
  // During reset, drive ready as 1
  // Else drive ready low for a clock low
  // for a read until the data is given back
  always @ (posedge clk) begin
    if (!rstn) begin
      ready <= 1;
    end else begin
      if (sel & ready_pe) begin
        ready <= 1;
      end
      if (sel & ready & !wr) begin
        ready <= 0;
      end
    end
  end

  // Drive internal signal accordingly
  always @ (posedge clk) begin
    if (!rstn) ready_dly <= 1;
    else       ready_dly <= ready;
  end

  assign ready_pe = ~ready & ready_dly;
endmodule

class driver extends uvm_driver #(reg_item);
  `uvm_component_utils(driver)
  function new(string name = "driver", uvm_component parent=null);
    super.new(name, parent);
  endfunction

  virtual reg_if vif;

  virtual function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    if (!uvm_config_db#(virtual reg_if)::get(this, "", "reg_vif", vif))
      `uvm_fatal("DRV", "Could not get vif")
  endfunction

  virtual task run_phase(uvm_phase phase);
    super.run_phase(phase);
    vif.sel <= 0;   // (añadido) valor inicial conocido
    forever begin
      reg_item m_item;
      `uvm_info("DRV", $sformatf("Wait for item from sequencer"), UVM_LOW)
      seq_item_port.get_next_item(m_item);
      drive_item(m_item);
      seq_item_port.item_done();
    end
  endtask

  virtual task drive_item(reg_item m_item);
    vif.sel   <= 1;
    vif.addr  <= m_item.addr;
    vif.wr    <= m_item.wr;
    vif.wdata <= m_item.wdata;
    @ (posedge vif.clk);
    while (!vif.ready) begin
      `uvm_info("DRV", "Wait until ready is high", UVM_LOW)
      @(posedge vif.clk);
    end

    vif.sel <= 0;
  endtask
endclass

class monitor extends uvm_monitor;
  `uvm_component_utils(monitor)
  function new(string name="monitor", uvm_component parent=null);
    super.new(name, parent);
  endfunction

  uvm_analysis_port #(reg_item) mon_analysis_port;
  virtual reg_if vif;
  semaphore sema4;

  virtual function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    if (!uvm_config_db#(virtual reg_if)::get(this, "", "reg_vif", vif))
      `uvm_fatal("MON", "Could not get vif")
    sema4 = new(1);
    mon_analysis_port = new ("mon_analysis_port", this);
  endfunction

  virtual task run_phase(uvm_phase phase);
    super.run_phase(phase);
    // This task monitors the interface for a complete
    // transaction and writes into analysis port when complete
    forever begin
      @ (posedge vif.clk);
      if (vif.sel) begin
        reg_item item = new;
        item.addr  = vif.addr;
        item.wr    = vif.wr;
        item.wdata = vif.wdata;

        if (!vif.wr) begin
          @(posedge vif.clk);
          item.rdata = vif.rdata;
        end
        `uvm_info(get_type_name(), $sformatf("Monitor found packet %s", item.convert2str()), UVM_LOW)
        mon_analysis_port.write(item);
      end
    end
  endtask
endclass

class scoreboard extends uvm_scoreboard;
  `uvm_component_utils(scoreboard)
  function new(string name="scoreboard", uvm_component parent=null);
    super.new(name, parent);
  endfunction

  reg_item refq[`DEPTH];   // modelo de referencia: última escritura por dirección
  uvm_analysis_imp #(reg_item, scoreboard) m_analysis_imp;

  virtual function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    m_analysis_imp = new("m_analysis_imp", this);
  endfunction

  // Corregido: "function void" (en la presentación falta el tipo de retorno)
  virtual function void write(reg_item item);
    if (item.wr) begin
      if (refq[item.addr] == null)
        refq[item.addr] = new;

      refq[item.addr] = item;
      `uvm_info(get_type_name(), $sformatf("Store addr=0x%0h wr=0x%0h data=0x%0h",
                item.addr, item.wr, item.wdata), UVM_LOW)
    end

    if (!item.wr) begin
      if (refq[item.addr] == null)
        if (item.rdata != 'h1234)
          `uvm_error(get_type_name(), $sformatf("First time read, addr=0x%0h exp=1234 act=0x%0h",
                     item.addr, item.rdata))
        else
          `uvm_info(get_type_name(), $sformatf("PASS! First time read, addr=0x%0h exp=1234 act=0x%0h",
                    item.addr, item.rdata), UVM_LOW)
      else
        if (item.rdata != refq[item.addr].wdata)
          `uvm_error(get_type_name(), $sformatf("addr=0x%0h exp=0x%0h act=0x%0h",
                     item.addr, refq[item.addr].wdata, item.rdata))
        else
          `uvm_info(get_type_name(), $sformatf("PASS! addr=0x%0h exp=0x%0h act=0x%0h",
                    item.addr, refq[item.addr].wdata, item.rdata), UVM_LOW)
    end
  endfunction
endclass

A2. Errores comunes y cómo resolverlos

UVM_FATAL [DRV] Could not get vif

El set y el get de uvm_config_db no coinciden en tipo, nombre o ruta. Revise: el tipo (virtual switch_if), el nombre ("switch_vif"), y que el test re-publique con "e0.a0.*" usando los mismos nombres de instancia que en create("e0", ...) y create("a0", ...).

UVM_FATAL [INVTST] Requested test from command line +UVM_TESTNAME=xxx not found

La clase no existe o no está registrada con `uvm_component_utils, o el paquete no se importa en tb_top.

Error de compilación: Identifier 'uvm_sequence_item' has not been declared o macros `uvm_* desconocidas

Falta -ntb_opts uvm-1.2, falta import uvm_pkg::*; o `include "uvm_macros.svh" en el paquete.

Error: tipo switch_if no declarado al compilar el paquete

El orden de files.f es incorrecto: la interfaz debe compilarse antes que el paquete.

Error de `timescale (“Timescale missing on this module”)

Algunos archivos tienen `timescale y otros no. Use solo la opción -timescale=1ns/1ps o ponga la directiva en todos los archivos.

La simulación termina en tiempo 0 sin tráfico

No se levantó la objeción en el test, o se bajó antes de arrancar la secuencia.

El scoreboard recibe menos transacciones que las generadas

La objeción se baja demasiado pronto, o el monitor pierde transacciones consecutivas (vea el ejercicio 7.1).

Randomization failed / el test se detiene con UVM_FATAL [TEST] Fallo al aleatorizar

Restricciones contradictorias, por ejemplo una restricción “dura” num inside {[2:5]} combinada con with {num inside {[20:30]}}. Use soft.
