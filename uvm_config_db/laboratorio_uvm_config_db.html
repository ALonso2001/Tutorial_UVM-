Laboratorio guiado: uvm_config_db en UVM

1 de octubre de 2026

1. Introducción y objetivos

Al terminar este laboratorio sabrás pasar cualquier dato (interfaces virtuales, objetos de configuración, enteros, strings) entre componentes UVM con uvm_config_db, predecir qué valor gana cuando hay varios set, y depurar un get que falla. El laboratorio dura unas 4 horas: 1 hora de teoría y 5 prácticas incrementales sobre un mismo testbench.

Objetivos de aprendizaje

  1. Explicar qué problema resuelve uvm_config_db y su relación con uvm_resource_db.
  2. Escribir llamadas set y get correctas, entendiendo cada argumento (contexto, inst_name, field_name, tipo).
  3. Construir el scope completo que genera un set y verificar si un get lo alcanza, incluyendo comodines.
  4. Aplicar las reglas de precedencia en build_phase y en tiempo de simulación.
  5. Diseñar un objeto de configuración por agente y propagarlo desde el test.
  6. Depurar con +UVM_CONFIG_DB_TRACE, print_config() y check_config_usage().
  7. Usar config_db desde secuencias y sincronizar cambios dinámicos con wait_modified().

Requisitos previos

  • SystemVerilog orientado a objetos: clases, parametrización, handles, virtual interface.
  • UVM básico: uvm_component, fases (build, connect, run), factory (type_id::create), agente con driver, monitor y secuenciador.
  • Un simulador con UVM 1.2 o IEEE 1800.2: Questa, VCS, Xcelium, Riviera-PRO o EDA Playground (gratuito, con Aldec Riviera-PRO).

Convenciones del laboratorio

  • Cada práctica tiene: objetivo, código base, tareas marcadas con // TODO, qué observar en el log, y solución.
  • Los fragmentos de código se acumulan: el testbench de la Práctica 1 se reutiliza en las siguientes.
  • Compila con +UVM_VERBOSITY=UVM_MEDIUM salvo que la práctica indique otra cosa.

2. Teoría I: qué es uvm_config_db y cómo funciona

uvm_config_db es una base de datos global, parametrizada por tipo, donde un componente publica un valor para un rango de la jerarquía y otro componente lo recupera por nombre. Resuelve un problema concreto: el test conoce la configuración, pero quienes la necesitan (driver, monitor, scoreboard) se crean varios niveles más abajo, y pasar argumentos por constructores rompería la factory.

2.1 Relación con uvm_resource_db

Debajo hay un único resource pool (uvm_resource_pool). uvm_resource_db es la interfaz de bajo nivel: guarda recursos con un scope de texto y un nombre. uvm_config_db es una capa encima que añade tres cosas:

  • Construye el scope a partir de un componente de contexto y una ruta relativa.
  • Aplica precedencia jerárquica durante build_phase (lo que se configura más arriba gana).
  • Ofrece wait_modified() para reaccionar a cambios.

Regla práctica: usa siempre uvm_config_db en testbenches; uvm_resource_db solo para recursos no jerárquicos y compartidos (por ejemplo, un registro de modelo global).

2.3 Cómo se forma el scope

El scope efectivo de un set es {cntxt.get_full_name(), ".", inst_name}. Si cntxt es null, se usa uvm_root y el scope es simplemente inst_name. Si inst_name es "", el scope es solo el nombre completo de cntxt.

Un get construye su propio nombre del mismo modo y busca recursos cuyo scope coincida con él (coincidencia por patrón, no por igualdad).

Ejemplos, con el test instanciado como uvm_test_top:

Llamada set (desde)Scope resultante¿Lo ve uvm_test_top.env.agt.drv?
set(this, "env.agt.drv", "n", 5) (test)uvm_test_top.env.agt.drvSí
set(this, "env.agt.*", "n", 5) (test)uvm_test_top.env.agt.*Sí, y también al monitor y al secuenciador
set(this, "agt", "n", 5) (env)uvm_test_top.env.agtNo: el driver es ...agt.drv, no ...agt
set(null, "uvm_test_top.*", "vif", vif) (módulo top)uvm_test_top.*Sí
set(null, "*", "vif", vif) (módulo top)*Sí (y todos los demás)
set(this, "", "n", 5) (agente)uvm_test_top.env.agtNo

2.4 Comodines y expresiones regulares

  • * coincide con cualquier secuencia de caracteres, incluidos puntos: env.* alcanza a todos los descendientes de env, a cualquier profundidad, pero no a env mismo.
  • ? coincide con un único carácter: env.agt? alcanza a agt0 y agt1.
  • Un inst_name entre barras se interpreta como expresión regular POSIX: "/^uvm_test_top\.env\.agt[0-3]\..*$/".
  • *agt* es un patrón frecuente pero peligroso: también alcanza a my_agt_cov o a cfg_agt_monitor.

2.5 Qué tipos se pueden guardar

Cualquier tipo de SystemVerilog: enteros, enums, strings, interfaces virtuales, handles de clase, arrays, structs. Atajos predefinidos:

typedef uvm_config_db #(uvm_bitstream_t) uvm_config_int;
typedef uvm_config_db #(string)          uvm_config_string;
typedef uvm_config_db #(uvm_object)      uvm_config_object;

Cuidado: uvm_config_int usa uvm_bitstream_t (un vector de 4096 bits), no int. Un uvm_config_int::set no lo recupera un uvm_config_db#(int)::get.

2.6 Cuándo llamar a set y get

  • set: en build_phase del padre, antes de crear (o al menos antes de que el hijo ejecute su build_phase). Desde el módulo top, en un initial antes de run_test().
  • get: en build_phase del componente que consume el valor (UVM ejecuta build_phase de arriba hacia abajo, así que el padre ya habrá hecho su set).
  • Para interfaces virtuales es habitual hacer el get en build_phase o connect_phase; nunca esperes a run_phase para descubrir que falta.

3. Teoría II: precedencia, configuración automática y errores comunes

Cuando varios set alcanzan al mismo get, gana el de mayor precedencia; durante build_phase la precedencia depende de la profundidad del contexto, y fuera de ella gana el último set. Esta sección explica la regla exacta y las trampas que causan la mayoría de fallos.

3.1 La regla de precedencia

Cada set crea un recurso con un valor numérico de precedencia:

  • Durante build_phase: precedencia = default_precedence (1000) − profundidad(cntxt). El test (uvm_test_top, profundidad 1) obtiene 999; el env (profundidad 2) obtiene 998; el agente, 997. Por eso el componente más alto en la jerarquía gana, aunque el hijo haga su set después.
  • Fuera de build_phase (antes de run_test() o en run_phase): precedencia = 1000 para todos.
  • Empate de precedencia: gana el set más reciente.

Si varios recursos coinciden con el nombre del get, UVM elige el de mayor precedencia y, entre iguales, el último insertado. La especificidad del patrón no importa: env.* y env.agt.drv compiten solo por precedencia.

// En my_test::build_phase  -> precedencia 999
uvm_config_db #(int)::set(this, "env.agt.drv", "delay", 10);
// En my_env::build_phase   -> precedencia 998
uvm_config_db #(int)::set(this, "agt.drv",     "delay", 2);
// El driver obtiene delay = 10: el test está más arriba.

Trampa importante: un set hecho desde el módulo top antes de run_test() no está en build_phase, así que obtiene precedencia 1000 y gana incluso al test. Si quieres que el test pueda sobrescribir algo publicado por el top, el test debe publicarlo con otro nombre o leerlo y republicarlo.

3.2 Valores frente a handles

Para tipos simples, set guarda una copia. Para clases, guarda el handle: si el test modifica el objeto después del set, quien hizo get ve el cambio, porque comparten el mismo objeto. Es útil (configuración compartida) y peligroso (un componente puede cambiar la configuración de otro). Si cada agente necesita su propia configuración, crea un objeto por agente.

3.3 Configuración automática con macros de campo

Si un componente registra campos con `uvm_field_* y llama a super.build_phase(phase), UVM invoca apply_config_settings(), que busca en la base de datos entradas con el mismo nombre que el campo y las asigna sin get explícito.

class my_driver extends uvm_driver #(my_item);
  int unsigned delay;
  `uvm_component_utils_begin(my_driver)
    `uvm_field_int(delay, UVM_DEFAULT)
  `uvm_component_utils_end

  function void build_phase(uvm_phase phase);
    super.build_phase(phase); // aquí se aplica la configuración automática
  endfunction
endclass

Limitaciones: solo reconoce tipos integrales (uvm_config_int, int, int unsigned), string y objetos publicados como uvm_object (uvm_config_object). No funciona con enums publicados con su propio tipo, interfaces virtuales ni clases publicadas con su tipo derivado. Además, recorre todos los recursos que coinciden con el componente y tiene un coste de rendimiento.

Recomendación del laboratorio: usa get explícito y comprueba su resultado. En IEEE 1800.2 puedes desactivar la configuración automática sobrescribiendo use_automatic_config() para que devuelva 0.

Respuestas: en el Experimento B, virtual interface simple_if es el mismo tipo que virtual simple_if (la palabra interface es opcional), así que funciona; con int falla en compilación porque no puedes pasar una variable de tipo interfaz virtual al argumento inout int. Si en cambio el set y el get usan tipos distintos pero compatibles con sus variables, el fallo es en simulación y silencioso: por eso es obligatorio comprobar el retorno.

5. Práctica 2: objeto de configuración del agente

Objetivo: agrupar toda la configuración de un agente en una sola clase, crearla en el test y publicarla con una única llamada set. Así el agente es reutilizable: el mismo código funciona activo o pasivo, con cualquier interfaz y cualquier temporización.

5.1 Diseño

El flujo de datos queda así:

  1. tb_top publica la interfaz solo para el test: set(null, "uvm_test_top", "vif", sif).
  2. El test lee la interfaz, crea simple_agent_cfg, rellena sus campos y la publica para el agente.
  3. El agente lee el objeto, decide si crea driver y secuenciador, y lo reenvía a sus hijos.
  4. Driver y monitor leen el objeto y toman de él la interfaz y los parámetros.

Ventaja: si mañana el agente necesita un parámetro nuevo, añades un campo a la clase y no tocas ninguna llamada set/get.

8. Práctica 5: config_db en secuencias y cambios dinámicos

Objetivo: configurar secuencias (que son objetos, no componentes) y reaccionar a cambios de configuración durante la simulación con wait_modified(). Cierra con cinco retos abiertos.

8.1 Leer configuración desde una secuencia

Una secuencia no tiene padre en la jerarquía, pero cuando se lanza con seq.start(sqr) su get_full_name() devuelve la ruta del secuenciador más su nombre, por ejemplo uvm_test_top.env.agt0.sqr.seq. Hay dos formas de leer:

FormaLlamada get en body()set correspondiente en el test
A. Por nombre completo de la secuenciaget(null, get_full_name(), "n_items", n_items)set(this, "env.agt0.sqr.*", "n_items", 8)
B. A través del secuenciadorget(m_sequencer, "", "n_items", n_items)set(this, "env.agt0.sqr", "n_items", 8)

La forma A permite configurar secuencias concretas por nombre ("env.agt0.sqr.burst_seq") e incluye las secuencias anidadas; la B configura por igual todo lo que corre en ese secuenciador.

Modifica simple_seq::body():

  1. uvm_test_top.env.agt*.drv.

  10. uvm_config_db#(int)::set(this, "env.agt0.sqr.burst_seq", "len", 16); (con el mismo tipo que use la secuencia).

9.3 Buenas prácticas

  • Comprueba siempre el retorno de get: uvm_fatal para lo obligatorio, valor por defecto para lo opcional.
  • Usa el mismo tipo en set y get; define typedef para interfaces virtuales parametrizadas.
  • Publica desde el top solo hacia el test ("uvm_test_top"), y deja que el test reparta. Evita set(null, "*", ...).
  • Agrupa la configuración en objetos: uno por agente y, si hace falta, uno por env que los contenga.
  • Usa el scope más estrecho posible; desconfía de patrones como "*agt*".
  • Recuerda que los objetos se comparten por handle: un objeto por instancia, salvo que quieras compartir a propósito.
  • No uses config_db para comunicación en tiempo de simulación entre componentes; para eso existen TLM, eventos o uvm_event_pool. wait_modified es para cambios de configuración puntuales.
  • Prefiere get explícito a la configuración automática de macros de campo.
  • Incluye +UVM_CONFIG_DB_TRACE y check_config_usage() en tu flujo de depuración habitual.
